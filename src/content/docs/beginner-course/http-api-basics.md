## 你会学到什么

这节帮你理解一次接口调用的完整过程：

- 什么是接口（API），为什么测试它
- 请求的组成：方法、URL、请求头、请求体
- 响应的组成：状态码、响应体（JSON）
- 一次请求从发起到返回经历了什么

学完后，你能看懂一个接口文档，也能解释清楚"我调了一个登录接口"这句话背后发生了什么。

一个建议：本节概念多，不必强求全部记住。学完把三样东西留下——**请求四要素（方法、URL、头、体）、状态码五族、三层断言**，其余当作查阅手册，用到时回来翻。

## 为什么要学

接口测试是测试开发的核心技能。原因很简单：

- **接口比页面稳定**：页面样式经常改，接口改得少，接口测试的维护成本低
- **接口比页面快**：一次接口调用几十毫秒，一次页面操作几秒，接口测试跑得动大批量用例
- **接口能测到页面测不到的东西**：非法参数、越权访问、边界值，这些在页面上点不出来，但接口可以直接构造

面试时"你怎么理解接口测试"是高频开场题，这节的概念就是你的答题素材。

补充一个数量级上的直觉。假设回归 300 个页面操作用例：UI 自动化跑一轮可能要一小时以上，还经常因为样式改动挂掉；等价的接口用例通常几分钟跑完，页面改版完全不影响它。这不是说 UI 测试没用——用户真正"看到"的东西只有 UI 能验证——而是说**能把大多数验证下沉到接口层的团队，反馈速度完全不在一个量级**。这也是[测试金字塔](/testdev-interview-site/glossary/test-pyramid/)强调"多接口、少 UI"的原因。

## 核心概念

### 什么是接口（API）

接口是前端和后端之间约定的"数据通道"。比如你在 App 上点"登录"：

1. 前端把你的账号密码打包成一个 **请求**，发给后端的一个地址
2. 后端校验后，返回一个 **响应**：成功就给你 token，失败就告诉你原因

接口测试就是跳过页面，直接用代码模拟前端发请求，然后检查后端的响应对不对。

### 请求方法

方法告诉服务器"你想做什么"。面试能讲清前两个就够用：

| 方法   | 语义                     | 典型场景               |
| ------ | ------------------------ | ---------------------- |
| GET    | 获取数据，不改服务器状态 | 查询用户信息、商品列表 |
| POST   | 提交数据，会创建或修改   | 登录、下单、注册       |
| PUT    | 整体更新一个资源         | 修改用户资料           |
| DELETE | 删除一个资源             | 删除订单               |

**GET 和 POST 的关键区别**：GET 的参数拼在 URL 里（`?page=1&size=10`），POST 的数据放在请求体里，URL 里看不到。所以密码这类敏感数据必须用 POST，这是安全常识。

### URL 的结构

一个接口地址可以拆成几部分：

```text
https://api.example.com/users/123?detail=true
└─┬─┘   └──────┬──────┘└───┬───┘└────┬────┘
 协议        域名         路径      查询参数
```

- **路径**（`/users/123`）：定位资源，123 通常是资源 ID
- **查询参数**（`?detail=true`）：附加条件，多个参数用 `&` 连接，是 GET 请求的"数据"

### 请求头（Headers）

请求头是请求的"说明信息"，测试时最常接触两个：

| 请求头        | 作用                   | 例子               |
| ------------- | ---------------------- | ------------------ |
| Content-Type  | 告诉服务器请求体的格式 | `application/json` |
| Authorization | 携带身份凭证           | `Bearer <token>`   |

调需要登录的接口时，就是在请求头里带上登录拿到的 token。

### 状态码

状态码是服务器对请求的"一句话总结"，分五族：

| 范围 | 含义       | 常见码                | 说明                                               |
| ---- | ---------- | --------------------- | -------------------------------------------------- |
| 2xx  | 成功       | 200 / 201             | 200 成功；201 创建成功                             |
| 3xx  | 重定向     | 301 / 302             | 资源搬家了，去新地址找                             |
| 4xx  | 客户端错误 | 400 / 401 / 403 / 404 | 400 参数错；401 未登录；403 无权限；404 地址不存在 |
| 5xx  | 服务端错误 | 500 / 502 / 503       | 服务器自己出问题了                                 |

**测试直觉**：4xx 多半是调用方的问题（参数错、没带 token），5xx 是服务器的 bug。看到 500，基本可以去提单了。

用登录场景把 4xx 的区分练熟，面试直接能用：

| 现象                   | 状态码                             | 含义               |
| ---------------------- | ---------------------------------- | ------------------ |
| 密码错误               | 401（或 200 + 业务码，看系统约定） | 身份验证没过       |
| 账号被禁用仍尝试登录   | 403（实现各有不同）                | 身份可识别但被拒绝 |
| 路径拼错成 `/api/logn` | 404                                | 地址不存在         |
| 请求体 JSON 格式非法   | 400                                | 参数解析失败       |

注意第一行：同样是"登录失败"，有的系统返回 401，有的统一返回 200 再用业务码区分。**断言什么，取决于被测系统的约定，而不是你背的标准**——所以写用例前的第一步永远是读接口文档、看联调环境的真实响应。

### JSON

JSON 是接口数据最常用的格式，规则就三条：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "token": "abc",
    "expire": 7200
  }
}
```

- 键值对：`"键": 值`，键必须加双引号
- 值可以是：数字、字符串、布尔、数组 `[]`、嵌套对象 `{}`、null
- 嵌套结构用 `.` 读：`data.token` 就是 `"abc"`

很多公司还会约定 **业务码**：HTTP 状态码只表示"请求送到了"，业务成功与否看响应体里的 `code`（比如 0 成功、1001 密码错误）。这就是为什么断言不能只看 200。

### Content-Type 必须和实际格式匹配

一个新手常见组合错误：请求体是 JSON，`Content-Type` 却写了 `application/x-www-form-urlencoded`（表单格式）。服务器按表单去解析一串 JSON 文本，得到的字段全是乱的，返回 400 或"参数缺失"。

| 你发送的数据                      | 应声明的 Content-Type               |
| --------------------------------- | ----------------------------------- |
| `{"user": "demo"}`（JSON 字符串） | `application/json`                  |
| `user=demo&age=18`（表单键值对）  | `application/x-www-form-urlencoded` |
| 文件上传                          | `multipart/form-data`               |

用 requests 时 `json=` 参数会自动带上正确的头，这也是推荐它的原因之一——少一个手工出错点。

### 一次请求的完整过程

```text
你的代码
  │  1. 组装请求（方法 + URL + 头 + 体）
  ▼
网络传输
  │  2. 找到服务器，送达请求
  ▼
服务器
  │  3. 校验参数 → 查数据库 → 执行逻辑
  ▼
你的代码
     4. 收到响应（状态码 + JSON 体）→ 断言
```

接口测试干预的就是第 1 步（构造各种请求）和第 4 步（验证响应）。中间的 2、3 步对测试来说是黑盒——这正是"接口测试是黑盒测试"的原因。

### 边界与陷阱：一个"只看 200"漏掉的反例

假设登录接口的实现是：无论密码对错，HTTP 都返回 200，响应体里用业务码区分——`code: 0` 成功，`code: 1001` 密码错误。现在有一个有 bug 的版本：密码错误时 `code` 误返回 0，还发了 token。

只断言状态码的用例：登录"密码错误"场景，看到 200，通过——**bug 完全漏掉**。
三层断言的用例：断言业务码应为 1001，实际是 0，立刻失败。

这个反例解释了为什么"三层断言"不是教条：每一层拦一类问题——状态码拦网络和路由问题，业务码拦逻辑错误，关键字段拦数据结构问题。少断一层，就有一类 bug 直接穿过你的测试。

## 最小示例

一个登录接口的请求和响应：

请求：

```json
POST /api/login
Content-Type: application/json

{"username": "demo", "password": "123456"}
```

逐行解读：

- `POST /api/login`：用 POST 方法，访问 `/api/login` 这个地址
- `Content-Type: application/json`：请求头，声明请求体是 JSON
- 最后一行是请求体：把账号密码发给服务器

响应：

```json
HTTP 200

{"code": 0, "message": "success", "data": {"token": "abc"}}
```

解读：

- `200`：HTTP 层面成功，请求被正常处理
- `code: 0`：业务层面成功，登录通过
- `data.token`：登录凭证，之后调其他接口要带在请求头里

**一次合格的接口测试，要断言三层**：状态码是 200、业务码 `code` 是 0、关键字段 `token` 存在且非空。只断言 200 会漏掉"密码错误也返回 200"这类业务失败。

再补一个 GET 请求的例子，重点看查询参数怎么参与断言：

```json
GET /get?city=wuhan&days=3

HTTP 200

{
  "args": {"city": "wuhan", "days": "3"},
  "headers": {"Accept": "*/*", "Host": "httpbin.org"}
}
```

解读：

- 查询参数会被服务器解析后放进响应的 `args` 里回显——这给了我们一个天然的断言点：发什么参数，就断言 `args` 里是什么
- 注意 `days` 回显的是字符串 `"3"` 而不是数字 3——查询参数没有类型，**断言时要按字符串比**，写成 `days == 3` 会失败，这是新手高频踩坑点
- `headers` 是服务器实际收到的请求头，排查"我发的头去哪了"时看这里

从"能跑"到"工程可用"的差距在这个例子里很具体：新手断言 `status_code == 200` 就结束；工程做法会再断言 `args["city"] == "wuhan"`，把"参数真的被服务端收到"也纳入验证。

## 手把手练习

**练习：用浏览器看一个真实的 GET 请求**

不用写代码，先把概念对应到真实请求上：

1. 浏览器打开 `https://httpbin.org/get?name=demo&age=18`
2. 观察 URL：路径是 `/get`，查询参数是 `name=demo` 和 `age=18`
3. 看页面返回的 JSON：找到 `args` 字段，里面就是你传的两个参数
4. 再把 URL 改成 `https://httpbin.org/status/404` 访问，观察浏览器显示什么

httpbin.org 是一个专门用来练习接口的公共服务：你发什么，它把收到的内容原样返回给你，非常适合观察"请求长什么样"。

**练习变体**：

- 变体 1（POST 练习）：浏览器地址栏只能发 GET，用命令行发一次 POST：`curl -X POST https://httpbin.org/post -H "Content-Type: application/json" -d '{"name":"demo"}'`，在返回 JSON 里找 `json` 字段，确认服务器收到了你的数据
- 变体 2（状态码练习）：依次访问 `httpbin.org/status/401`、`/status/403`、`/status/500`，对照本节状态码表说出每个码的含义
- 变体 3（鉴权练习）：访问 `https://httpbin.org/basic-auth/demo/123456`（不带凭证），观察 401 响应和它的 `WWW-Authenticate` 头——这正是下一节登录小项目要用的接口族

**预期输出**：变体 1 的返回里应有 `"json": {"name": "demo"}`，说明请求体被正确解析；把 `-H` 那个头去掉重发，`json` 字段会变成 `null`——这就是"Content-Type 与实际格式不匹配"的现场演示。

## 检查标准

完成本节的标准：

- 你能说出 GET 和 POST 的区别（参数位置、语义）
- 你看到 400、401、404、500 能说出大致含义
- 你能解释为什么断言不能只看状态码 200
- 你能读懂一个 JSON 响应，找到嵌套字段的值
- 你能说出 Content-Type 和请求体格式不匹配时的典型症状
- 你知道查询参数回显没有类型，断言数字时要按字符串比

## 常见错误

**错误 1：认为状态码 200 就是业务成功**

很多接口把所有响应都返回 200，成功失败只看响应体里的 `code`。断言只看 200，等于没测业务逻辑。

**错误 2：GET 请求把敏感数据放 URL**

GET 参数在 URL 里明文可见，会被浏览器历史、服务器日志记录。密码、token 永远不要用 GET 传。

**错误 3：混淆 401 和 403**

401 是"没登录"（缺少身份），403 是"登录了但没权限"。记法：401 先解决"你是谁"，403 才是"你不能干这个"。

**错误 4：响应不是 JSON 还调 .json()**

```text
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

接口返回 500 错误页（HTML）或空响应时，`.json()` 解析不了就抛这个错。排查步骤：①先 `print(response.status_code)` 和 `print(response.text)` 看原始内容；②确认是"接口真坏了"还是"你调错了地址"；③写测试时对非 2xx 响应先断状态码、再解析 JSON，让失败发生在正确的位置。

**错误 5：把 400 和 422 混为一谈**

不少框架（如 FastAPI）参数校验失败返回 422 而不是 400，按"400 才是参数错"写断言就会误判。排查方法：看接口文档约定，或在联调环境故意发一次非法参数、观察真实状态码。**期望值来自被测系统的实际行为，不来自通用标准**——这条原则同样适用于业务码。

## 面试怎么说

如果面试官问："你怎么理解接口测试？"，可以回答：

"接口测试是跳过页面、直接调用后端接口来验证功能的方式。我会关注请求的方法、URL、请求头和请求体，断言时除了 HTTP 状态码，还会检查响应体里的业务码和关键字段，因为有些系统业务失败也返回 200。相比 UI 测试，接口测试更稳定、执行更快，适合覆盖大量场景。"

这个回答展示了你知道接口测试"测什么"和"为什么值得测"，而不是只会背概念。

**追问 1**："GET 和 POST 除了参数位置还有什么区别？"

参考回答："语义上 GET 是读操作，幂等、可缓存，重复请求结果一样；POST 是写操作，可能改变服务器状态，天然不该缓存。一个直观体现：刷新 GET 请求浏览器敢直接重发，刷新 POST 会弹确认框——就是在防重复提交。"

**追问 2**："接口测试为什么比 UI 测试稳定？"

参考回答："两个原因：一是接口契约的变更频率远低于页面样式，改动少失败就少；二是接口测试不依赖浏览器渲染，没有元素定位这种脆弱环节。所以团队实践通常是接口层覆盖绝大多数业务规则，UI 只留主流程冒烟。"
