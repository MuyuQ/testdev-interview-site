## 一句话定义

接口断言（API Assertion）是自动化测试中验证 API 响是否符合预期的技术手段，通过多维度校验（状态码、响应体、响应头、响应时间等）确保接口行为正确性，是接口自动化测试的核心能力。

## 为什么测试开发要关心它

接口断言直接决定自动化测试能否发现真实问题，影响：

1. **缺陷检出能力**：断言覆盖不全会导致漏测，断言过细会导致测试脆弱
2. **测试稳定性**：合理的断言策略能减少误报，提升团队对自动化的信任度
3. **维护成本**：过度断言会导致测试用例频繁修改，投入产出比失衡
4. **定位效率**：分层断言能快速定位问题在哪个环节（网络/接口/业务/数据）

**一句话：断言写得好，bug 跑不了；断言写得差，天天修脚本。**

## 它在真实工作流中的位置

```
需求评审 → 【识别断言点：哪些业务逻辑需要验证】
    ↓
接口设计 → 【明确响应结构：确定断言目标字段】
    ↓
用例设计 → 【设计断言策略：状态断言 + 业务断言 + 数据断言】
    ↓
脚本开发 → 【实现断言代码：选择断言方法、处理断言失败】
    ↓
调试执行 → 【验证断言有效性：故意破坏数据验证断言能发现】
    ↓
CI/CD → 【断言结果输出：测试报告、失败截图、日志定位】
```

测试开发在以下场景应用接口断言：

- **接口自动化测试**：核心工作，每天都要写断言
- **接口监控**：线上接口健康检查，需要快速有效的断言
- **契约测试**：验证接口是否符合前后端约定的契约
- **性能测试**：验证高并发下响应数据的正确性

## 一个最小例子

### 场景：用户登录接口

假设有一个登录 API，返回结构如下：

```json
// POST /api/login
// 成功响应
{
  "code": 0,
  "message": "success",
  "data": {
    "userId": 1001,
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "nickname": "测试用户"
  }
}

// 失败响应（密码错误）
{
  "code": 1001,
  "message": "用户名或密码错误",
  "data": null
}
```

### 分层断言示例

```javascript
const { expect } = require('chai');

describe('登录接口断言示例', () => {
  it('登录成功 - 分层断言', async () => {
    const response = await request(app)
      .post('/api/login')
      .send({ username: 'testuser', password: 'correct_password' });

    // ========== 第一层：状态断言 ==========
    // 验证 HTTP 协议层面是否正常
    expect(response.status).to.equal(200);                    // 状态码
    expect(response.headers['content-type']).to.match(/json/); // 响应类型
    expect(response.duration).to.be.below(1000);               // 响应时间

    // ========== 第二层：业务断言 ==========
    // 验证业务逻辑处理结果
    expect(response.body.code).to.equal(0);                    // 业务状态码
    expect(response.body.message).to.equal('success');         // 业务消息

    // ========== 第三层：数据断言 ==========
    // 验证返回数据的具体内容
    expect(response.body.data).to.have.property('userId');    // 字段存在
    expect(response.body.data.userId).to.be.a('number');      // 类型正确
    expect(response.body.data.token).to.match(/^eyJ/);        // JWT 格式
    expect(response.body.data.nickname).to.have.length.above(0); // 非空
  });

  it('登录失败 - 业务错误断言', async () => {
    const response = await request(app)
      .post('/api/login')
      .send({ username: 'testuser', password: 'wrong_password' });

    // 状态断言：HTTP 层面成功
    expect(response.status).to.equal(200);

    // 业务断言：业务层面失败
    expect(response.body.code).to.equal(1001);
    expect(response.body.message).to.include('密码错误');

    // 数据断言：敏感信息不应返回
    expect(response.body.data).to.be.null;
  });
});
```

### 断言类型对比

| 断言类型 | 验证目标 | 示例 | 发现的问题类型 |
|---------|---------|------|--------------|
| **状态断言** | HTTP 协议层 | 状态码、响应头、响应时间 | 服务不可用、超时、网络问题 |
| **业务断言** | 业务逻辑层 | code 字段、message 字段 | 业务逻辑错误、参数校验失败 |
| **数据断言** | 数据内容层 | 字段存在性、类型、格式、值 | 数据结构变更、字段缺失、格式错误 |

## 面试怎么说

**基础版（校招）**：

> "接口断言是验证 API 响应是否符合预期。我通常会验证状态码是否为 200、返回数据是否包含期望的字段。比如登录接口，我会断言返回的 token 字段存在且格式正确。"

**进阶版（社招）**：

> "接口断言要分层设计：首先是状态断言，验证 HTTP 状态码和响应时间，确保接口可用；然后是业务断言，验证业务状态码和消息，确保业务逻辑正确；最后是数据断言，验证具体字段的存在性、类型和值。
>
> 在实际项目中，我发现很多测试只断言状态码 200，结果业务逻辑出错却没发现。所以我会特别关注业务断言的设计，确保每个接口的核心业务逻辑都有对应断言。"

**高级版（测试专家）**：

> "接口断言的核心难点在于找到「有效覆盖」和「稳定可维护」的平衡点。过度断言会导致测试脆弱，每次接口改动都要修脚本；断言不足又会导致漏测。
>
> 我的实践原则是：
> 1. **核心字段必须断言**：业务关键字段如 code、message、核心数据
> 2. **派生字段选择性断言**：如计算字段、格式化字段，关注边界值
> 3. **动态字段跳过断言**：如时间戳、随机 ID，用正则或类型断言
> 4. **敏感字段重点断言**：如脱敏后的手机号、脱敏后的金额
>
> 同时，我会设计断言失败的详细信息输出，包括期望值、实际值、字段路径，让定位问题更高效。"

## 易错点

1. **只断言状态码**：HTTP 200 不等于业务成功，很多业务错误也返回 200，只是 code 字段不同。

2. **断言响应体全部字段**：过度断言会导致测试脆弱，接口改个字段名就挂一批用例。

3. **忽略断言失败信息**：断言失败时没有输出期望值和实际值，排错效率极低。

4. **断言写死具体值**：如断言 `userId === 1001`，换了测试环境就失败。应该断言类型或格式。

5. **混淆接口测试和 UI 测试断言**：接口断言关注数据正确性，UI 断言关注展示正确性，两者不同。

6. **忽略响应头断言**：某些场景下响应头很重要，如 `Content-Type`、`Set-Cookie`、`Cache-Control`。

## 容易混淆的概念

| 概念 | 定义 | 区别 |
|------|------|------|
| **状态断言** | 验证 HTTP 协议层面的正确性 | 关注网络传输层，如状态码、响应时间 |
| **业务断言** | 验证业务逻辑处理的正确性 | 关注业务结果，如 code、message 字段 |
| **数据断言** | 验证响应数据的具体内容 | 关注数据本身，如字段值、类型、格式 |
| **契约断言** | 验证响应是否符合前后端约定 | 关注接口契约，如 Schema 验证 |
| **软断言** | 一个失败后继续执行其他断言 | 用于收集所有错误再统一报告 |
| **硬断言** | 失败立即停止当前测试 | 用于关键断言，失败后无意义继续 |

## 自测题

1. **选择题**：以下哪个场景需要同时使用状态断言和业务断言？
   - A. 验证接口是否可访问
   - B. 验证接口响应时间
   - C. 验证登录接口返回的用户信息正确
   - D. 验证响应头是否包含特定字段

   <details>
   <summary>点击查看答案</summary>
   答案：C。登录接口需要状态断言确保请求成功，业务断言确保登录逻辑正确（如返回有效 token）。A 只需状态断言，B 只需响应时间断言，D 只需响应头断言。
   </details>

2. **判断题**：接口返回 `{"code": -1, "message": "余额不足"}` 但 HTTP 状态码是 200，断言状态码为 200 就能发现这个问题。

   <details>
   <summary>点击查看答案</summary>
   答案：错误。HTTP 200 只表示请求被成功处理，不代表业务成功。这个场景需要业务断言验证 code 字段为 -1 表示业务失败。
   </details>

3. **简答题**：如何设计一个转账接口的断言策略？

   <details>
   <summary>点击查看答案</summary>

   转账接口断言策略：
   1. **状态断言**：HTTP 200，响应时间 < 2s（涉及资金操作需要快速响应）
   2. **业务断言**：
      - 成功场景：code = 0，message 包含"成功"
      - 失败场景：余额不足时 code = 业务错误码，message 提示余额不足
   3. **数据断言**：
      - 返回的流水号格式正确
      - 转账金额与请求一致
      - 转账时间在合理范围内
   4. **数据库断言**（可选）：验证余额是否正确扣减
   5. **幂等性断言**：重复请求返回相同结果
   </details>
