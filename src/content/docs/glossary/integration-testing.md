## 一句话定义

集成测试（Integration Testing）是在单元测试通过后，将多个已测试的模块按照设计规格组合在一起，验证它们之间的接口交互、数据传递和协作行为是否正确的测试活动。

## 为什么测试开发要关心它

集成测试是测试金字塔中承上启下的关键层次：

1. **发现单元测试无法发现的问题**：单元测试隔离了外部依赖，模块间的接口契约、数据格式、异常处理等问题只能在集成测试中暴露

2. **成本效益的平衡点**：相比端到端测试，集成测试定位问题更精准、执行更快、维护成本更低；相比单元测试，它能发现更真实的缺陷

3. **持续集成中的质量守门员**：CI流水线中，集成测试是合并代码前的关键质量关卡

4. **接口契约验证的核心手段**：微服务架构下，服务间接口的正确性直接影响系统稳定性

## 它在真实工作流中的位置

```
开发阶段：单元测试 → 【集成测试】 → 系统测试 → 验收测试
                        ↑
                   你的工作重点
```

在实际项目中：
- **开发提测前**：开发自测完成集成测试用例
- **持续集成流水线**：每次代码合并触发集成测试
- **版本发布前**：集成测试作为冒烟测试的一部分
- **缺陷修复后**：针对修复模块重新执行相关集成测试

## 一个最小例子

假设我们有一个电商系统的订单模块和库存模块：

```javascript
// 订单服务调用库存服务的接口
async function createOrder(orderData) {
  // 1. 调用库存服务扣减库存
  const inventoryResponse = await fetch('/api/inventory/deduct', {
    method: 'POST',
    body: JSON.stringify({
      productId: orderData.productId,
      quantity: orderData.quantity
    })
  });

  // 2. 处理库存服务返回结果
  if (!inventoryResponse.ok) {
    throw new Error('库存扣减失败');
  }

  // 3. 创建订单记录
  const order = await OrderRepository.create(orderData);
  return order;
}
```

**集成测试用例设计**：

```javascript
describe('订单-库存模块集成测试', () => {
  it('当库存充足时，应成功创建订单并扣减库存', async () => {
    // 准备测试数据
    const orderData = { productId: 'P001', quantity: 2 };
    const initialStock = await getStock('P001'); // 100

    // 执行被测方法
    const order = await createOrder(orderData);

    // 验证结果
    expect(order.id).toBeDefined();
    const finalStock = await getStock('P001');
    expect(finalStock).toBe(initialStock - 2); // 98
  });

  it('当库存不足时，应返回明确错误信息', async () => {
    const orderData = { productId: 'P002', quantity: 1000 };

    await expect(createOrder(orderData))
      .rejects
      .toThrow('库存扣减失败');
  });
});
```

这个例子展示了**接口集成**的验证：订单模块正确调用库存模块API，并正确处理返回结果。

## 面试怎么说

"集成测试在我的理解中，是验证模块间协作正确性的测试层次。在实际项目中，我会从三个维度来设计集成测试：

第一是**接口集成**，验证模块间API调用的入参出参、异常处理、超时重试等契约符合性；

第二是**数据集成**，验证数据在模块间流转时的一致性，比如上游写入的数据下游能否正确读取；

第三是**业务流程集成**，验证跨模块的业务场景能否正确走通，比如用户下单到支付完成的链路。

我通常会采用**增量集成策略**，先测试核心模块间的集成，再逐步扩展到周边模块，这样既能保证质量又控制了测试成本。"

## 易错点

1. **边界条件遗漏**：只测试正常路径，忽略接口超时、网络中断、数据格式错误等边界情况

2. **测试数据污染**：集成测试使用共享数据库，测试数据互相影响导致偶发性失败

3. **过度Mock**：为了隔离依赖过度使用Mock，导致集成测试失去意义

4. **层次混淆**：把集成测试写成端到端测试，覆盖范围过大导致定位困难

5. **忽视幂等性**：测试用例没有考虑重复执行的场景，导致测试无法自动化运行

6. **忽略数据一致性**：只验证接口返回，没有验证数据库中数据的最终状态

## 容易混淆的概念

| 概念 | 关注点 | 测试范围 | 举例 |
|------|--------|----------|------|
| **单元测试** | 单个函数/方法的逻辑正确性 | 最小代码单元 | 验证 `calculateTotal()` 计算逻辑 |
| **集成测试** | 模块间接口、数据、协作正确性 | 多个模块组合 | 验证订单模块调用库存模块 |
| **系统测试** | 完整系统的功能和非功能需求 | 整个系统 | 验证用户下单到收货的完整流程 |
| **端到端测试** | 用户真实场景的端到端流程 | 全链路 | 模拟用户在浏览器中完成购物 |

**关键区分**：
- 单元测试**隔离依赖**，集成测试**连接依赖**
- 集成测试**定位模块间问题**，系统测试**验证整体功能**
- 端到端测试**模拟真实用户**，集成测试**聚焦技术接口**

## 自测题

1. 你的团队准备开发一个"用户注册后自动发送欢迎邮件"的功能，请列出至少3个需要验证的集成点。

<details>
<summary>点击查看参考答案</summary>

需要验证的集成点：
1. **用户服务 ↔ 消息队列**：用户注册成功后，用户服务是否正确发送消息到消息队列
2. **消息队列 ↔ 邮件服务**：邮件服务是否正确消费队列中的消息
3. **邮件服务 ↔ SMTP服务器**：邮件服务是否正确调用外部邮件发送接口
4. **数据一致性**：邮件发送失败时，是否有重试机制和状态记录
5. **异常处理**：消息队列宕机时，用户注册是否受影响（降级策略）

</details>

2. 判断题：集成测试应该覆盖所有模块的所有组合方式。

<details>
<summary>点击查看参考答案</summary>

**错误**。集成测试应该有策略地选择关键集成点进行测试，而非穷举所有组合。原因：
- 组合爆炸问题：N个模块可能产生大量组合
- 应采用**增量集成策略**：先测试核心模块间集成，逐步扩展
- 关注**高风险集成点**：涉及金额、权限、数据同步等关键路径
- 平衡**投入产出比**：根据模块间耦合度决定测试深度

</details>
