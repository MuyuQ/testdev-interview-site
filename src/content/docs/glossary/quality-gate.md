## 一句话定义

质量门禁（Quality Gate）是一组预定义的质量标准集合，代码必须**全部满足**这些标准才能"通关"进入下一阶段，如合并到主分支或部署到生产环境。

把它理解成地铁进站口的闸机最贴切：你（代码）必须刷卡成功（通过所有检查）才能进站，任何一项不达标闸机就挡住你。它不是建议，是**强制关卡**。

## 为什么重要

质量门禁是软件工程中的"守门员"，它将质量要求从"事后补救"转变为"事前预防"。其核心价值在于：

1. **防止劣质代码流入**：在问题进入主分支前拦截，降低修复成本（越早发现问题，修复成本越低，业界常引用"需求阶段发现问题的修复成本是生产环境的 1/100"的量级差异）
2. **统一团队质量标准**：将质量要求代码化、可视化，避免"人治"带来的主观差异——新人老人一个尺度
3. **快速反馈**：开发者能在几分钟内知道代码是否符合标准，而非等到发布当天才发现问题
4. **降低人工审查负担**：自动化检查处理机械性规则（格式、覆盖率、漏洞），让人力专注于更有价值的逻辑与架构审查
5. **质量数据可追溯**：每次门禁的通过/失败数据可以沉淀为趋势图，帮团队量化"质量是在变好还是变坏"

没有质量门禁的团队，往往面临"测试环境一塌糊涂、生产环境事故频发"的窘境。

## 它在真实工作流中的位置

质量门禁通常部署在 CI/CD 流水线的**关键决策节点**：

```
代码提交 → 【门禁1：PR检查】 → 代码合并 → 构建 → 【门禁2：预发布检查】 → 部署 → 【门禁3：生产健康检查】
```

**常见门禁位置**：

| 位置     | 时机       | 典型检查项                       |
| -------- | ---------- | -------------------------------- |
| PR门禁   | 代码合并前 | 单元测试、代码规范、基础安全扫描 |
| 构建门禁 | 镜像构建后 | 集成测试、依赖漏洞扫描           |
| 部署门禁 | 部署前     | 性能基准测试、安全合规检查       |
| 生产门禁 | 部署后     | 健康检查、冒烟测试、监控告警     |

一个关键认知：**门禁越靠前，拦截成本越低**。PR 阶段拦住一个空指针，成本是开发者改几行；生产环境因为同样的问题宕机，成本可能是客诉、资损和加班。

## 质量门禁的常见指标

不同门禁关卡关注不同维度，以下是实战中最常用的几类指标与参考阈值：

| 指标类别 | 代表性指标             | 常见阈值（参考） | 拦截的问题                |
| -------- | ---------------------- | ---------------- | ------------------------- |
| 测试     | 单元测试通过率         | 100%             | 功能回退、基础逻辑错误    |
| 测试     | 代码覆盖率             | 行覆盖 70%~80%   | 大量未受保护的代码路径    |
| 质量     | 重复率（Duplication）  | < 5%             | 复制粘贴代码、维护噩梦    |
| 质量     | 圈复杂度（Cyclomatic） | 单函数 < 15      | 难以测试、易出 bug 的逻辑 |
| 安全     | 依赖漏洞               | 无 High/Critical | 已知 CVE、供应链攻击      |
| 规范     | Lint / 风格            | 0 error          | 风格不一致、明显坏味道    |
| 性能     | 构建/启动耗时          | 不超基线 20%     | 性能劣化悄悄混入          |

**注意**：阈值不是越严越好。一个刚落地门禁的团队如果一上来要求覆盖率 90%，开发者会为了达标写一堆无意义的 `assert true`，门禁变成形式主义。建议从"能拦住真问题"的宽松阈值起步，随团队成熟度逐步收紧。

## 最小例子

以下是一个典型的 PR 质量门禁配置（以 GitHub Actions 为例）：

```yaml
# .github/workflows/quality-gate.yml
name: Quality Gate
on: [pull_request]

jobs:
  quality-gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 安装依赖
        run: npm ci

      - name: 代码规范检查
        run: npm run lint

      - name: 单元测试（覆盖率 ≥ 80%）
        run: npm test -- --coverage --coverageThreshold='{"global":{"lines":80}}'

      - name: 安全漏洞扫描
        run: npm audit --audit-level=high
```

这段配置定义了一个简单的质量门禁：只有当代码通过 lint 检查、单元测试覆盖率达到 80%、且无高危安全漏洞时，PR 才能合并。任意一步失败，整个 job 标红，合并按钮被锁定。

**第二个例子：SonarQube 质量门禁**（更贴近企业实践）：

```properties
# sonar-project.properties 中定义的门禁条件（Quality Gate Conditions）
sonar.qualitygate.condition1=coverage<80  # 覆盖率低于80%则不通过
sonar.qualitygate.condition2=new_bugs>0    # 新增 bug 数大于0则不通过
sonar.qualitygate.condition3=vulnerabilities>0  # 存在漏洞则不通过
```

SonarQube 的优势在于它区分"存量"和"增量"——你可以只对新提交的代码设严格门禁（新代码覆盖率必须 80%），对历史债务逐步治理，避免一上来被存量问题压垮。

### 门禁失败之后：处理流程比拦截本身更重要

门禁红了之后怎么办，决定团队对门禁的长期态度。一套可执行的处理流程：

```text
1. fail-fast：PR 检查按"lint → 单测 → 覆盖率 → 安全扫描"串行短路，第一处失败立即终止，
   报告只推第一个问题，避免一屏无关报错掩盖根因
2. 定责到人：失败通知直接推给提交者（不是群发到群里），要求 15 分钟内响应
3. 唯一豁免通道：紧急 hotfix 可申请豁免合并，但必须登记债务单（写明"何时补"）、双人复核代码，
   豁免记录在周报可见
4. 债务闭环：豁免单必须在下个迭代关闭，逾期自动升级到技术负责人，防止"先合进去再说"变成常态
```

设计红线是**让"绕过门禁"比"修复问题"更麻烦**——豁免要有登记、有复核、有期限。一旦绕过门禁零成本、零记录，门禁制度就名存实亡了。

## 门禁的分层与递进策略

质量门禁不是"一个关卡"，而是一套**由松到紧的递进防线**：

1. **提交级（最快，秒~分钟）**：本地 pre-commit 跑 lint + 单测，最快反馈。谁都能跑，不通过根本提交不出去。
2. **PR 级（分钟级）**：CI 跑完整单测 + 覆盖率 + 安全扫描，作为合并闸门。
3. **构建/部署级（分钟~十分钟）**：集成测试、契约测试、性能基准，确保可交付。
4. **生产级（持续）**：健康检查 + 冒烟 + 监控告警，确保线上真的没问题。

经验法则：**越靠后的门禁，检查越重、频率越低**。你不会每次提交都跑一遍全链路压测，但每次提交都应该跑单测。

## 面试怎么说

"质量门禁是我们在 CI/CD 流水线中设置的质量关卡。以我参与的项目为例，我们在 PR 阶段配置了代码规范检查、单元测试（覆盖率要求 80%）和安全扫描三项门禁指标。只有全部通过，代码才能合并到主分支。

这套机制帮我们拦截了大约 30% 的潜在问题，大大减轻了后续测试和审查的压力。我记得有一次，门禁扫描出一个依赖包的高危漏洞，我们在合并前就完成了升级，避免了上线后的安全风险。

如果面试官追问细节，我会强调两点：第一，门禁是**分层的**，提交级求快、部署级求全；第二，阈值要**渐进式收紧**，不能一上来就卡死团队。我认为质量门禁的核心价值是'左移'——把问题拦截在尽可能早的阶段。"

## 易错点

1. **门禁指标过于宽松**：设置"装饰性"门禁（如覆盖率仅要求 10%），实际起不到拦截作用，沦为心理安慰
2. **门禁指标过于严格**：初始就要求 100% 覆盖率，导致开发者疲于应对，反而抵触门禁制度，甚至偷偷绕过
3. **缺少快速失败机制**：所有检查串行执行，一个失败后仍跑完其他检查，浪费时间和资源（应 `fail-fast`）
4. **门禁与开发流程脱节**：本地没有对应检查，开发者只能等 CI 结果才知道问题，反馈链路太长
5. **忽视门禁执行效率**：门禁运行时间过长（如超过 30 分钟），开发节奏被打断，团队开始"盲合并"
6. **只看单一指标**：只盯覆盖率，结果开发者写出高覆盖但无断言的测试（"假绿"）。门禁要组合多个维度交叉验证

7. **简历误用："我们的门禁保证了线上零故障"**
   - 门禁只能拦截"可自动化检测"的问题，逻辑设计缺陷、环境差异、数据脏乱大多拦不住，"零故障"这种说法会被追问具体拦截案例，一问就穿
   - 加分表述：讲清楚门禁实际拦过什么（覆盖率不达标、高危漏洞、接口回归失败），以及哪些问题门禁无能为力、靠什么机制补位（代码评审、灰度发布、线上监控）——知道工具的边界，比神化工具有说服力

## 容易混淆的概念

| 概念                     | 区别                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| **质量门禁 vs 代码审查** | 门禁是自动化检查，代码审查是人工审查。两者互补，门禁处理可量化规则，审查处理逻辑和设计问题 |
| **质量门禁 vs 测试**     | 测试是门禁的组成部分之一。门禁还包含规范检查、安全扫描、性能基准等非测试检查项             |
| **质量门禁 vs 质量基线** | 门禁是动态检查机制，基线是静态标准文档。门禁是基线的可执行化                               |
| **质量门禁 vs 发布审批** | 门禁是技术检查，审批是流程决策。门禁为审批提供客观数据支撑                                 |
| **质量门禁 vs 监控告警** | 门禁发生在"交付前"（预防），监控告警发生在"运行中"（发现），两者是事前事后的闭环           |

1. 为什么质量门禁要设置在代码合并前，而不是合并后？

2. 如果团队反馈质量门禁运行太慢影响开发效率，你会如何优化？

3. 一个项目应该设置多少个质量门禁？太少或太多各有什么问题？

4. **场景题**：团队刚接入门禁，你作为负责人应该如何设置第一版覆盖率阈值？

   <details>
   <summary>点击查看答案</summary>

   不建议一上来就卡 80%~90%。建议：第一版用偏松但能拦真问题的阈值（如 60%，或仅对**新代码**要求 80%），让团队先养成"提交即达标"的习惯；同时把"增量覆盖率"和"存量覆盖率"分开统计，新代码的门禁可以严，历史代码给过渡期。门禁的目标是建立信任，而不是制造阻力——阈值要在"拦得住问题"和"不误伤开发"之间找平衡，再随成熟度逐步收紧。
   </details>

5. **判断题**：质量门禁只要保证"单元测试 100% 通过"就足够保障质量了。

   <details>
   <summary>点击查看答案</summary>

   错误。单测 100% 通过只能说明已有测试都没 regression，但完全可能"测了错的或没测重点"。如果测试没有有效断言（只调用不验证），或者覆盖率虽高但核心分支没覆盖，门禁照样"假绿"。需要配合覆盖率、复杂度、漏洞扫描等多维度指标交叉验证。
   </details>

## 面试官追问

**追问 1：「紧急修复线上事故，能不能跳过门禁直接合并？」**

> 参考回答：可以走"豁免"，但不能"裸奔"。事故处理的第一优先级是止血，流程上必须留快速通道：双人复核 + 只跑最快的冒烟子集 + 登记债务单，合并后 24 小时内补齐完整验证。设计的关键是把"跳过"变成"记账"——豁免有留痕、有期限、有升级机制，下个迭代必须闭环。反过来讲，如果没有这条通道，事故压力下的人一定会绕过门禁且不留任何记录，那比有豁免通道危险得多。这个题考的不是"守规矩"还是"变通"，是能不能设计一个兼顾两者的流程。

**追问 2：「开发为了过覆盖率门禁写了大量无效测试，怎么破？」**

> 参考回答：先承认这是指标设计问题，不是人的问题——只考核覆盖率数量，就一定得到刷数量。治理三招：第一，加维度交叉，断言密度（每千行测试代码的断言数）或变异测试得分，无断言的测试立刻现形；第二，覆盖率只卡"新代码/改动代码"，不给历史债务留续命的通道，同时堵住"给生成代码补测试凑数"这类动作；第三，评审抽查测试质量：评审员随机抽 2 个用例问"这个用例挂了说明什么"，答不上来就说明用例无意义。指标组合拳比单纯调阈值有效得多。

**追问 3：「门禁误报多，团队吵着要放宽阈值，你怎么办？」**

> 参考回答：先用数据分类，再决定是修门禁还是修代码。把近一个月的门禁失败拉出来分三类：真问题（拦对了）、误报（规则不合理，比如 flaky 用例污染门禁）、阈值确实过高。真问题占比高就顶住压力不动阈值，同时把 flaky 用例隔离出门禁（重试机制 + 标记追踪），让信号先变干净；误报占比高就修规则，并把修复过程同步给团队——让大家看到"提异议有用，但要用数据说话"。最差的做法是吵赢了就静默改阈值，那会一次性消耗掉门禁制度的全部信用。
