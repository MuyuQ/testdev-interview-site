## 一句话定义

质量门禁（Quality Gate）是一组预定义的质量标准集合，代码必须全部满足这些标准才能"通关"进入下一阶段，如合并到主分支或部署到生产环境。

## 为什么重要

质量门禁是软件工程中的"守门员"，它将质量要求从"事后补救"转变为"事前预防"。其核心价值在于：

1. **防止劣质代码流入**：在问题进入主分支前拦截，降低修复成本（越早发现问题，修复成本越低）
2. **统一团队质量标准**：将质量要求代码化、可视化，避免"人治"带来的主观差异
3. **快速反馈**：开发者能在几分钟内知道代码是否符合标准，而非等到发布当天才发现问题
4. **降低人工审查负担**：自动化检查处理机械性规则，让人力专注于更有价值的逻辑审查

没有质量门禁的团队，往往面临"测试环境一塌糊涂、生产环境事故频发"的窘境。

## 工作流位置

质量门禁通常部署在 CI/CD 流水线的关键决策节点：

```
代码提交 → 【门禁1：PR检查】 → 代码合并 → 构建 → 【门禁2：预发布检查】 → 部署 → 【门禁3：生产健康检查】
```

**常见门禁位置**：

| 位置 | 时机 | 典型检查项 |
|------|------|-----------|
| PR门禁 | 代码合并前 | 单元测试、代码规范、基础安全扫描 |
| 构建门禁 | 镜像构建后 | 集成测试、依赖漏洞扫描 |
| 部署门禁 | 部署前 | 性能基准测试、安全合规检查 |
| 生产门禁 | 部署后 | 健康检查、冒烟测试、监控告警 |

## 最小例子

以下是一个典型的 PR 质量门禁配置（以 GitHub Actions 为例）：

```yaml
# .github/workflows/quality-gate.yml
name: Quality Gate
on: [pull_request]

jobs:
  quality-gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 安装依赖
        run: npm ci

      - name: 代码规范检查
        run: npm run lint

      - name: 单元测试（覆盖率 ≥ 80%）
        run: npm test -- --coverage --coverageThreshold='{"global":{"lines":80}}'

      - name: 安全漏洞扫描
        run: npm audit --audit-level=high
```

这段配置定义了一个简单的质量门禁：只有当代码通过 lint 检查、单元测试覆盖率达到 80%、且无高危安全漏洞时，PR 才能合并。

## 面试怎么说

"质量门禁是我们在 CI/CD 流水线中设置的质量关卡。以我参与的项目为例，我们在 PR 阶段配置了代码规范检查、单元测试（覆盖率要求 80%）和安全扫描三项门禁指标。只有全部通过，代码才能合并到主分支。这套机制帮我们拦截了大约 30% 的潜在问题，大大减轻了后续测试和审查的压力。

我记得有一次，门禁扫描出一个依赖包的高危漏洞，我们在合并前就完成了升级，避免了上线后的安全风险。所以我认为质量门禁的核心价值是'左移'——把问题拦截在尽可能早的阶段。"

## 易错点

1. **门禁指标过于宽松**：设置"装饰性"门禁（如覆盖率仅要求 10%），实际起不到拦截作用
2. **门禁指标过于严格**：初始就要求 100% 覆盖率，导致开发者疲于应对，反而抵触门禁制度
3. **缺少快速失败机制**：所有检查串行执行，一个失败后仍跑完其他检查，浪费时间和资源
4. **门禁与开发流程脱节**：本地没有对应检查，开发者只能等 CI 结果才知道问题
5. **忽视门禁执行效率**：门禁运行时间过长（如超过 30 分钟），影响开发节奏

## 混淆概念

| 概念 | 区别 |
|------|------|
| **质量门禁 vs 代码审查** | 门禁是自动化检查，代码审查是人工审查。两者互补，门禁处理可量化规则，审查处理逻辑和设计问题 |
| **质量门禁 vs 测试** | 测试是门禁的组成部分之一。门禁还包含规范检查、安全扫描、性能基准等非测试检查项 |
| **质量门禁 vs 质量基线** | 门禁是动态检查机制，基线是静态标准文档。门禁是基线的可执行化 |
| **质量门禁 vs 发布审批** | 门禁是技术检查，审批是流程决策。门禁为审批提供客观数据支撑 |
