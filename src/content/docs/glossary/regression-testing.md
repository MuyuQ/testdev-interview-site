## 一句话定义

回归测试是在软件发生变更（如 Bug 修复、新功能添加、代码重构）后，重新执行已有测试用例，以验证变更是否引入新缺陷或导致原有功能异常的测试活动。

## 为什么测试开发要关心它

回归测试是质量保障的最后一道防线，直接关系到软件的稳定性和用户体验。测试开发需要关注回归测试的原因：

1. **成本控制**：每次全量回归成本极高，需要设计高效的回归策略
2. **自动化落地**：回归测试是自动化测试最主要的应用场景
3. **风险评估**：需要判断哪些范围需要回归，哪些可以跳过
4. **持续集成**：在 CI/CD 流程中，回归测试是质量门禁的核心

## 它在真实工作流中的位置

```
代码提交 → 代码审查 → 单元测试 → 【回归测试】 → 预发布验证 → 生产部署
                                    ↓
                              发现问题 → 缺陷修复 → 再次回归
```

回归测试通常位于：
- **提交阶段**：每次代码合并前的快速回归
- **每日构建**：夜间定时执行的完整回归
- **发布前验证**：版本发布前的全面回归验证

## 一个最小例子

### 场景：电商系统优惠券功能修复

假设修复了一个优惠券计算的 Bug，以下是回归测试的设计：

```javascript
// 1. 直接验证修复点 - 优惠券金额计算
describe('优惠券修复回归', () => {
  // 验证 Bug 修复
  it('应该正确计算满减优惠券金额', () => {
    const order = { total: 100, coupon: 'FULL_MINUS_20' };
    expect(calculateDiscount(order)).toBe(20);
  });

  // 2. 回归关联功能 - 验证修改没有影响其他优惠券类型
  it('折扣券计算应该保持正常', () => {
    const order = { total: 100, coupon: 'DISCOUNT_80' };
    expect(calculateDiscount(order)).toBe(20); // 100 * 0.2
  });

  // 3. 回归订单流程 - 验证整体流程未受影响
  it('订单提交时优惠券应该正确应用', () => {
    const cart = createCart([{ price: 100, quantity: 1 }], 'FULL_MINUS_20');
    const result = submitOrder(cart);
    expect(result.finalPrice).toBe(80);
  });
});
```

### 回归范围选择策略

```python
# 基于代码变更影响范围选择回归用例
def select_regression_tests(changed_files, test_suite):
    """
    根据代码变更选择回归测试范围
    """
    affected_modules = analyze_dependencies(changed_files)

    # 策略1: 精准回归 - 只选择受影响模块的用例
    precise_tests = [
        test for test in test_suite
        if test.module in affected_modules
    ]

    # 策略2: 风险优先 - 高风险模块优先回归
    risk_based_tests = sorted(
        precise_tests,
        key=lambda t: t.risk_score,
        reverse=True
    )

    return risk_based_tests
```

**标准回答模板：**

"回归测试是在软件变更后验证原有功能不受影响的测试活动。在我的项目中，我们采用了分层的回归策略：

1. **快速回归**：每次提交执行核心用例，约 5 分钟完成
2. **日级回归**：每晚执行功能模块的完整回归
3. **版本回归**：发布前执行全量回归

## 易错点

### 1. 回归测试 = 重新执行所有测试

**错误认知**：认为回归测试必须执行全部测试用例

**正确理解**：回归测试的核心是"验证原有功能"，范围选择应基于风险分析。全量回归成本极高，应采用增量回归或精准回归策略。

### 2. 只测试修改点，忽略关联影响

**错误做法**：修复了优惠券 Bug，只测试优惠券功能

**正确做法**：
- 分析代码依赖关系
- 识别可能受影响的关联模块
- 将关联模块纳入回归范围

### 3. 忽视回归用例的维护

**常见问题**：随着版本迭代，回归用例越来越多，执行时间失控

**解决方案**：
- 定期清理过时用例
- 合并重复用例
- 设立用例准入和退出机制

## 容易混淆的概念

| 概念 | 定义 | 与回归测试的区别 |
|------|------|------------------|
| **回归测试** | 验证变更后原有功能正常 | 核心关注"变化后的影响" |
| **重新测试** | 修复后验证原缺陷已解决 | 只关注"这个 Bug 修好没" |
| **确认测试** | 验证缺陷是否真正修复 | 是重新测试的另一种说法 |
| **冒烟测试** | 快速验证基本功能可用 | 是回归测试的子集 |

**区别示例**：
- 重新测试：修复登录 Bug 后，测试登录是否正常
- 回归测试：修复登录 Bug 后，测试登录以及注册、支付等是否正常
- 冒烟测试：每天早上快速验证核心功能能跑通
