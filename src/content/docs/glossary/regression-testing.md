## 一句话定义

回归测试是在软件发生变更（如 Bug 修复、新功能添加、代码重构）后，重新执行已有测试用例，以验证变更是否引入新缺陷或导致原有功能异常的测试活动。

## 为什么测试开发要关心它

回归测试是质量保障的最后一道防线，直接关系到软件的稳定性和用户体验。测试开发需要关注回归测试的原因：

1. **成本控制**：每次全量回归成本极高，需要设计高效的回归策略
2. **自动化落地**：回归测试是自动化测试最主要的应用场景
3. **风险评估**：需要判断哪些范围需要回归，哪些可以跳过
4. **持续集成**：在 CI/CD 流程中，回归测试是质量门禁的核心

## 它在真实工作流中的位置

```
代码提交 → 代码审查 → 单元测试 → 【回归测试】 → 预发布验证 → 生产部署
                                    ↓
                              发现问题 → 缺陷修复 → 再次回归
```

回归测试通常位于：

- **提交阶段**：每次代码合并前的快速回归
- **每日构建**：夜间定时执行的完整回归
- **发布前验证**：版本发布前的全面回归验证

## 一个最小例子

### 场景：电商系统优惠券功能修复

假设修复了一个优惠券计算的 Bug，以下是回归测试的设计：

```javascript
// 1. 直接验证修复点 - 优惠券金额计算
describe("优惠券修复回归", () => {
  // 验证 Bug 修复
  it("应该正确计算满减优惠券金额", () => {
    const order = { total: 100, coupon: "FULL_MINUS_20" };
    expect(calculateDiscount(order)).toBe(20);
  });

  // 2. 回归关联功能 - 验证修改没有影响其他优惠券类型
  it("折扣券计算应该保持正常", () => {
    const order = { total: 100, coupon: "DISCOUNT_80" };
    expect(calculateDiscount(order)).toBe(20); // 100 * 0.2
  });

  // 3. 回归订单流程 - 验证整体流程未受影响
  it("订单提交时优惠券应该正确应用", () => {
    const cart = createCart([{ price: 100, quantity: 1 }], "FULL_MINUS_20");
    const result = submitOrder(cart);
    expect(result.finalPrice).toBe(80);
  });
});
```

### 回归范围选择策略

```python
# 基于代码变更影响范围选择回归用例
def select_regression_tests(changed_files, test_suite):
    """
    根据代码变更选择回归测试范围
    """
    affected_modules = analyze_dependencies(changed_files)

    # 策略1: 精准回归 - 只选择受影响模块的用例
    precise_tests = [
        test for test in test_suite
        if test.module in affected_modules
    ]

    # 策略2: 风险优先 - 高风险模块优先回归
    risk_based_tests = sorted(
        precise_tests,
        key=lambda t: t.risk_score,
        reverse=True
    )

    return risk_based_tests
```

### 真实项目里，回归集的分级维护

成熟团队的回归套件不是一锅端，而是**分级清单**，触发时机各不相同：

| 回归集     | 内容                        | 规模参考           | 触发时机                 |
| ---------- | --------------------------- | ------------------ | ------------------------ |
| 冒烟集     | 核心主链路 P0 用例          | 5~15 条，10 分钟内 | 每次部署后               |
| 快速回归集 | 变更模块 + 强关联模块用例   | 50~200 条          | 每次 PR 合并前           |
| 全量回归集 | 全部功能 + 历史故障场景     | 全部用例           | 版本发布前、大版本合并后 |
| 补丁回归集 | 每个 Bug 修复沉淀的复现用例 | 持续累积           | 随快速/全量回归执行      |

其中"补丁回归集"最容易被忽视：**每个修复过的 Bug，它的复现步骤就是一条现成的回归用例**。把历史 Bug 的复现用例沉淀进回归集，相当于让每个踩过的坑都变成永久守卫——这是回归套件最有价值的增长方式，也是"回归用例从哪来"这个面试题的标准答案之一：缺陷沉淀 + 需求评审产出 + 历史故障反推，三条来源缺一不可。

## 面试怎么说

**标准回答模板：**

"回归测试是在软件变更后验证原有功能不受影响的测试活动。在我的项目中，我们采用了分层的回归策略：

1. **快速回归**：每次提交执行核心用例，约 5 分钟完成
2. **日级回归**：每晚执行功能模块的完整回归
3. **版本回归**：发布前执行全量回归

我们通过代码依赖分析和风险打分来实现精准回归，将回归用例数量减少了 60%，同时保持缺陷检出率不变。自动化回归测试覆盖率达到了 85%。"

**进阶话题引导：**

- 谈论回归测试与重构的关系
- 分享自动化回归测试的维护成本控制经验
- 讨论如何衡量回归测试的有效性

## 易错点

### 1. 回归测试 = 重新执行所有测试

**错误认知**：认为回归测试必须执行全部测试用例

**正确理解**：回归测试的核心是"验证原有功能"，范围选择应基于风险分析。全量回归成本极高，应采用增量回归或精准回归策略。

### 2. 只测试修改点，忽略关联影响

**错误做法**：修复了优惠券 Bug，只测试优惠券功能

**正确做法**：

- 分析代码依赖关系
- 识别可能受影响的关联模块
- 将关联模块纳入回归范围

### 3. 忽视回归用例的维护

**常见问题**：随着版本迭代，回归用例越来越多，执行时间失控

**解决方案**：

- 定期清理过时用例
- 合并重复用例
- 设立用例准入和退出机制

### 4. 简历误用："回归用例数减少 60%，缺陷检出率不变，自动化覆盖率 85%"

三个数字连着说很漂亮，但面试官会立刻追问：砍掉的 60% 用例怎么保证不漏？用什么依据判断"检出率不变"？如果答不出风险分级依据和影响分析方法，数字反而成了扣分项。加分做法：准备一个具体决策例子——"某次改动涉及优惠券计算，我按调用链圈出订单、结算两个模块的用例进快速回归，砍掉的是低频配置类页面用例，并在后续三个版本里验证了砍掉部分没有逃逸缺陷"。用决策过程而不是结果数字立住可信度。

## 容易混淆的概念

| 概念         | 定义                         | 与回归测试的区别                                                                                       |
| ------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------ |
| **回归测试** | 验证变更后原有功能正常       | 核心关注"变化后的影响"                                                                                 |
| **重新测试** | 修复后验证原缺陷已解决       | 只关注"这个 Bug 修好没"                                                                                |
| **确认测试** | 验证缺陷是否真正修复         | 是重新测试的另一种说法                                                                                 |
| **冒烟测试** | 快速验证基本功能可用         | 是回归测试的子集                                                                                       |
| **灰度验证** | 新版本先放量给小部分用户验证 | 与回归互补：回归在发布前拦问题，灰度在发布后用真实流量验证；灰度期发现问题仍要走"修复→回归→再放量"闭环 |

**区别示例**：

- 重新测试：修复登录 Bug 后，测试登录是否正常
- 回归测试：修复登录 Bug 后，测试登录以及注册、支付等是否正常
- 冒烟测试：每天早上快速验证核心功能能跑通

## 面试官追问

**追问 1：「全量回归要跑 6 小时，版本窗口只有 2 小时，你怎么砍？」**

> 参考回答：按信息增量砍，不按比例砍。第一步按变更影响分析圈必跑集：这次改了哪些模块、动了哪些共享组件和配置，关联用例一条不省；第二步历史故障优先：出过线上问题的场景用例保留；第三步看用例的"近期捕获记录"：连续多个版本没发现过问题且逻辑简单的低风险用例，降频到日级或版本级跑；第四步工程提速兜底：失败重试、用例并行、按模块分片。关键纪律是砍下来的每一批用例都要有记录和复审机制——降频不等于删除，下个版本风险变了要能调回来。

**追问 2：「回归通过率长期 99%，但线上还是出问题，说明什么？」**

> 参考回答：先查四类缺口。断言缺口：用例跑了但只断言状态码不断言数据，接口"成功"但业务错了；环境缺口：回归环境和生产的配置、数据量级差异大，容量和性能类问题测不出来；场景缺口：真实用户的操作序列、脏数据、并发时序没被用例表达；时机缺口：问题出在灰度放量或线上配置变更，而回归只在发布前跑。把每个线上问题回溯归类到这四类里，缺口集中的方向就是下季度补强的方向——这道题考的是"会不会用逃逸数据反推策略"，能主动讲出分析方法就赢了。

**追问 3：「自动化回归越积越多、维护不动了，怎么平衡？」**

> 参考回答：把回归集当产品经营，不当仓库堆积。三个机制：准入机制——新用例进回归集要过三条评审：断言是否有效、能否独立运行、失败是否可定位，不过不进；退出机制——连续多个版本无捕获且维护成本高于价值的用例降频或归档，用捕获率数据说话；所有权机制——每个模块的回归用例有明确 owner，模块变更时 owner 负责同步用例，避免"人人用、没人养"。落地节奏是每季度做一次回归集体检：执行时长、失败率、捕获率三个指标过一遍，该删的删、该降频的降频。
