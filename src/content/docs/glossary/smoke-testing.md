## 一句话定义

冒烟测试（Smoke Testing）是一种轻量级的测试方法，在软件构建或部署后，快速验证**核心业务主链路**是否正常工作，判断软件是否"值得继续测试"。

名字来源于硬件测试：通电后看设备冒不冒烟，不冒烟说明基本能跑，再深入测。软件同理——先确认主链路没"着火"，再投入大量回归资源。

## 为什么测试开发要关心它

1. **快速反馈**：几分钟内发现阻塞性缺陷，避免团队在"坏掉"的版本上浪费时间
2. **节省成本**：在执行全面回归测试前，先筛掉明显不可用的版本，把贵的回归留给"活着的"版本
3. **CI/CD 守门员**：作为流水线的质量门禁，阻止劣质代码流入后续阶段
4. **团队协作**：开发提测前的自测标准，减少测试人员的无效工作
5. **降低风险敞口**：生产发布后第一时间跑冒烟，能最快发现"部署成功了但功能挂了"的事故

## 它在真实工作流中的位置

```
代码提交 → 单元测试 → 构建 → 部署到测试环境
                                    ↓
                              【冒烟测试】 ← 快速验证主链路
                                    ↓
                           通过 → 执行完整回归测试
                           失败 → 打回，开发修复后重新提测
```

在 CI/CD 流水线中，冒烟测试通常配置在**部署后、完整测试套件前**，作为"是否继续"的判断条件。一次发布的标准动作是：部署 → 冒烟 → 通过才跑回归 → 通过才发布。

## 冒烟用例的选择标准

冒烟测试最怕两件事：选太多（变得和回归一样慢）、选太少（漏掉关键链路）。实战中选用例遵循"三优先"：

1. **主链路优先**：用户最高频、最赚钱的路径。电商就是"登录→搜索→加购→下单→支付"；IM 就是"注册→登录→发消息→收消息"。
2. **高频功能优先**：日活最高的功能，出问题影响面最大。
3. **历史故障点优先**：曾经出过 P0/P1 事故的功能，必须纳入冒烟，防止复发。

同时遵守"三不选"：**不选**纯边界/异常场景（留给回归）、**不选**低频长尾功能、**不选**需要复杂数据准备的用例（冒烟要快）。

经验值：一个中型系统的冒烟套件控制在 **5~15 个用例、10 分钟以内**完成。

## 最小例子

假设一个电商系统的主链路是：登录 → 搜索商品 → 加入购物车 → 下单 → 支付。

```python
# smoke_test.py - 冒烟测试示例
import pytest
from api_client import APIClient

class TestSmoke:
    """电商系统冒烟测试 - 验证主链路"""

    def test_user_journey_smoke(self):
        """验证用户完整购买流程能否走通"""
        client = APIClient()

        # 1. 用户登录
        login_resp = client.login("test_user", "password123")
        assert login_resp.status_code == 200, "登录失败，主链路中断"

        # 2. 搜索商品
        search_resp = client.search_products("iPhone")
        assert search_resp.status_code == 200, "搜索失败"
        assert len(search_resp.json()["items"]) > 0, "无搜索结果"

        # 3. 加入购物车
        product_id = search_resp.json()["items"][0]["id"]
        cart_resp = client.add_to_cart(product_id, quantity=1)
        assert cart_resp.status_code == 200, "加购失败"

        # 4. 创建订单
        order_resp = client.create_order()
        assert order_resp.status_code == 200, "下单失败"
        order_id = order_resp.json()["order_id"]

        # 5. 支付（测试环境模拟）
        pay_resp = client.mock_payment(order_id)
        assert pay_resp.status_code == 200, "支付失败"

        print("冒烟测试通过，主链路畅通")
```

运行配置（CI/CD 中）：
```yaml
# .gitlab-ci.yml
stages:
  - build
  - smoke
  - regression

smoke_test:
  stage: smoke
  script:
    - pytest tests/smoke/ -v --tb=short
  timeout: 10m  # 冒烟测试必须快速
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

## 手工冒烟 vs 自动化冒烟

| 维度 | 手工冒烟 | 自动化冒烟 |
|------|---------|-----------|
| 执行者 | 测试/开发人工点 | CI 自动跑 |
| 速度 | 慢（分钟~小时） | 快（分钟级） |
| 稳定性 | 受人为因素影响 | 结果可复现 |
| 适用场景 | 提测前的探索性确认 | CI/CD 流水线、每次部署后 |
| 成本 | 重复劳动、易遗漏 | 一次编写、长期受益 |

建议：**主链路一律自动化**，纳入流水线；手工冒烟只作为探索性测试的补充，不依赖它做"放行决策"。

## 冒烟测试的触发策略

什么时候跑冒烟？三种典型触发点：

- **提测触发**：开发提交测试申请后自动跑，不通过直接打回
- **部署触发**：每次部署到测试/预发/生产环境后自动跑，作为"部署健康检查"
- **定时触发**：对线上核心链路做周期性冒烟（如每小时），作为轻量监控

关键是要让冒烟**失败能立刻告警到人**，而不是等测试人员第二天才发现。

## 面试怎么说

"冒烟测试是我在项目中用来保障版本基本可用性的第一道防线。在 CI/CD 流水线中，我会把它配置在部署后、完整回归测试前，用几分钟快速验证核心业务主链路。比如电商系统，我会验证用户登录、搜索商品、加入购物车、下单支付这个完整链路能否跑通。冒烟测试的核心原则是**快速**和**聚焦主链路**，不追求覆盖边界场景，而是快速判断版本是否值得继续深入测试。"

**可以补充的亮点**：
- 举例说明冒烟测试帮团队拦截了多少次严重问题
- 说明冒烟测试用例的选择标准（主链路、高频功能、历史故障点）
- 提及冒烟测试与监控告警的结合

## 易错点

1. **把冒烟测试写成全面测试**：冒烟测试不是"什么都测"，而是聚焦主链路，控制在 5-15 分钟内完成
2. **忽视失败后的快速反馈**：冒烟测试失败必须立即通知开发，而不是等测试人员发现
3. **用例维护不及时**：核心业务变化后，冒烟测试用例未同步更新，导致漏测或无效测试
4. **过度依赖 UI 层**：冒烟测试可以走 API 层，比 UI 自动化更快更稳定
5. **混淆"冒烟"与"健全"测试**：冒烟测试更粗粒度，健全测试（Sanity Testing）则是对特定功能的深入验证
6. **把装饰性检查当冒烟**：只查"首页能打开"不算冒烟，必须走通**业务主链路**，否则"页面在但下单挂了"发现不了

## 容易混淆的概念

| 概念 | 定义 | 区别要点 |
|------|------|----------|
| **冒烟测试** | 验证主链路是否畅通 | 范围最窄，速度最快，判断"值不值得测" |
| **健全测试** | 验证特定功能模块是否正常 | 范围稍广，针对变更部分深入验证 |
| **回归测试** | 验证变更是否影响已有功能 | 范围最广，覆盖全面，耗时最长 |
| **单元测试** | 验证最小代码单元 | 由开发执行，关注代码逻辑 |

简单记忆：**冒烟 → 健全 → 回归**，范围由窄到宽，时间由短到长。

## 自测题

1. **选择题**：一个 APP 新版本发布，以下哪个最适合作为冒烟测试用例？
   - A. 验证设置页每个开关的边界值
   - B. 验证用户能否注册、登录、发布一条动态
   - C. 验证所有错误提示文案
   - D. 验证弱网下的超时重试

   <details>
   <summary>点击查看答案</summary>
   答案：B。注册→登录→发动态是核心主链路，符合冒烟"快速验证值不值得测"的定位。A、C 是细节/边界（留给回归），D 是异常场景（不是冒烟首选）。
   </details>

2. **判断题**：冒烟测试因为范围窄，所以可以只检查"首页能打开"就算通过。

   <details>
   <summary>点击查看答案</summary>
   错误。只查首页打开是"部署存活检查"，不是冒烟。冒烟必须走通**业务主链路**（如登录→下单→支付），否则"页面在、核心功能挂了"这种最致命的问题会被放过。
   </details>

3. **设计题**：你接手一个新项目，没有任何冒烟测试，第一周你会怎么搭建？

   <details>
   <summary>点击查看答案</summary>
   步骤：① 和产品/开发对齐核心主链路（用户最高频路径）；② 挑选 5~10 个覆盖主链路的用例，优先走 API 层（快且稳）；③ 接入 CI，部署后自动触发，超时 10 分钟内；④ 失败即告警到人；⑤ 随业务迭代维护用例，不追求一次覆盖全。
   </details>
