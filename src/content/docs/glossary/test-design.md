## 一句话定义

测试设计是确定测试目标、选择合适的测试方法、设计高质量测试用例的系统性过程，是连接测试需求与测试执行的关键桥梁。

## 为什么测试开发要关心它

测试设计直接决定了测试的有效性和效率。好的测试设计能够：

- **用最少的用例覆盖最多的风险**，避免冗余测试浪费资源
- **发现隐蔽缺陷**，边界值和异常场景往往是 Bug 的重灾区
- **提升面试竞争力**，大厂必问测试设计方法，体现基本功
- **指导自动化测试策略**，知道测什么才能更好地设计自动化框架

## 它在真实工作流中的位置

```
需求分析 → 测试设计 → 用例编写 → 用例评审 → 测试执行 → 缺陷报告
              ↑
          （核心环节）
```

测试设计处于需求分析和用例编写之间，是将业务需求转化为可执行测试用例的关键环节。测试开发工程师在这个阶段需要：

1. 分析需求的输入输出、约束条件
2. 选择合适的测试设计方法（等价类、边界值、场景法等）
3. 产出结构化的测试用例

## 一个最小例子

### 场景：用户年龄输入框（限制 18-65 岁）

```javascript
// 测试设计方法应用示例

// 1. 等价类划分
// 有效等价类：18-65 岁（选 30 作为代表）
// 无效等价类：<18 岁、>65 岁、非数字、空值

const equivalenceClassTests = [
  { input: 30, expected: "valid", desc: "有效等价类代表值" },
  { input: 17, expected: "invalid", desc: "无效等价类-小于下界" },
  { input: 66, expected: "invalid", desc: "无效等价类-大于上界" },
  { input: "abc", expected: "invalid", desc: "无效等价类-非数字" },
];

// 2. 边界值分析
// 边界点：18、65
// 边界±1：17、19、64、66
// 补充：边界点外再取一点：0、100

const boundaryTests = [
  { input: 17, expected: "invalid", desc: "下边界-1" },
  { input: 18, expected: "valid", desc: "下边界点" },
  { input: 19, expected: "valid", desc: "下边界+1" },
  { input: 64, expected: "valid", desc: "上边界-1" },
  { input: 65, expected: "valid", desc: "上边界点" },
  { input: 66, expected: "invalid", desc: "上边界+1" },
];

// 3. 场景法
// 基本流：正常输入年龄 → 提交成功
// 备选流1：输入无效年龄 → 提示错误
// 备选流2：未输入直接提交 → 提示必填
// 备选流3：连续输入错误 → 账户锁定

const scenarioTests = [
  {
    name: "正常注册流程",
    steps: ["进入注册页", "输入有效年龄30", "点击提交"],
    expected: "注册成功",
  },
  {
    name: "异常流程-年龄超限",
    steps: ["进入注册页", "输入年龄10", "点击提交"],
    expected: "提示年龄不符合要求",
  },
];
```

### 第四种常用方法：判定表（多条件组合的场景）

当一个结果由**多个条件组合**决定时，等价类和边界值会漏，判定表最有效。以规则「满 100 减 20，且会员才能叠加运费券」为例：

```text
条件桩：C1 订单金额 ≥ 100    C2 是会员    C3 已使用运费券
动作桩：A1 减 20             A2 允许叠加运费券

| 规则         | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 |
|-------------|----|----|----|----|----|----|----|----|
| C1 满 100    | Y  | Y  | Y  | Y  | N  | N  | N  | N  |
| C2 是会员    | Y  | Y  | N  | N  | Y  | Y  | N  | N  |
| C3 已用运费券 | Y  | N  | Y  | N  | Y  | N  | Y  | N  |
|-------------|----|----|----|----|----|----|----|----|
| A1 减 20     | √  | √  | √  | √  | ×  | ×  | ×  | ×  |
| A2 叠加      | ×  | √  | ×  | ×  | -  | -  | -  | -  |
```

8 条规则里可以化简：C1 为 N 时 C2、C3 不影响结果（R5~R8 合并成一条"不满 100"用例），得到精简用例集。判定表的价值在于**强迫你枚举组合**——"满 100 但已用过运费券能不能减"这类需求文档没写清楚的角落，画表时自然暴露，还能顺手拿这张表去和产品对齐需求，一举两得。

## 面试怎么说

"测试设计是测试开发的核心技能之一。我主要掌握三种经典方法：

**等价类划分**的核心思想是将输入域划分为若干等价类，每个等价类中的数据对于揭露错误是等效的。比如一个年龄输入 18-65，有效等价类选一个代表值就行，无效等价类要分别考虑低于下界和高于上界。

**边界值分析**是我最常用的方法，因为大量缺陷发生在边界附近。对于闭区间 [a, b]，我会测试 a-1、a、a+1、b-1、b、b+1 这些点。

**场景法**更贴近用户视角，我会从基本流出发，逐步叠加备选流来设计场景。比如登录功能，正常登录是基本流，密码错误、账号不存在、连续失败锁定都是备选流。

在项目中，我通常会组合使用这些方法，先用等价类划分减少冗余，再用边界值分析补充边界点，最后用场景法覆盖业务流程。"

## 易错点

1. **等价类划分遗漏无效等价类**
   只考虑有效输入，忘记测试无效输入（如非数字、空值、特殊字符），导致缺陷遗漏。

2. **边界值分析不完整**
   只测边界点本身，忘记边界±1；或者混淆开闭区间，导致边界判断错误。

3. **场景法只关注正常流程**
   设计测试时过度关注"快乐路径"，忽视异常场景和错误处理，而这恰恰是 Bug 高发区。

4. **盲目追求数量**
   认为测试用例越多越好，实际上冗余用例不仅浪费测试时间，还稀释了真正有价值的测试。

5. **方法选择僵化**
   不同场景适合不同方法，比如逻辑复杂的业务用场景法，输入输出明确的功能用等价类和边界值。

6. **简历误用："我熟练运用等价类、边界值、场景法设计用例"**
   - 这句话人人会写，区分度在追问：「订单满 100 减 20、上限 50，你怎么设计用例？」答不出"金额档位边界 + 减免上限边界 + 判定表组合"的分层思路就露馅
   - 加分做法：面试前把一个熟悉的业务（登录、优惠券、购物车）用三种方法各推一遍，能现场画判定表、报出边界点序列，比罗列方法名词有说服力

## 容易混淆的概念

| 概念       | 定义                                   | 关键区别                   |
| ---------- | -------------------------------------- | -------------------------- |
| 等价类划分 | 将输入域划分为若干等价类，每类选代表值 | 关注**分类**，减少冗余     |
| 边界值分析 | 在边界附近选取测试值                   | 关注**边界**，发现边界缺陷 |
| 场景法     | 从用户视角模拟使用场景                 | 关注**流程**，贴近业务     |

**常见混淆：边界值 vs 等价类**

等价类是"分类"思维，把输入分成几块，每块选一个代表；边界值是"边界"思维，专门在边界附近挖 Bug。两者是互补关系，不是替代关系。

**常见混淆：黑盒测试方法 vs 白盒测试方法**

等价类、边界值、场景法都是黑盒测试方法，不需要了解内部实现；语句覆盖、分支覆盖、路径覆盖是白盒测试方法，需要看到代码逻辑。

## 面试官追问

**追问 1：「给你一个登录框，现场设计用例，你怎么切维度？」**

> 参考回答：我会先声明框架再展开，避免想到哪说到哪。功能与等价类：正确凭据、错误密码、不存在账号、空输入、大小写与首尾空格处理。边界与格式：用户名/密码长度上下界及其 ±1、特殊字符、emoji、超长字符串。安全维度：SQL 注入、XSS 脚本、暴力破解锁定与验证码、密码明文传输与回显。状态与流程：连续失败锁定后能否解锁、验证码过期、多端登录互踢。体验与兼容：提示文案是否泄露"账号不存在还是密码错误"、浏览器与分辨率适配。最后补非功能：弱网、重复点击、并发登录。先框架后展开，是这类题被当作基本功试金石的原因。

**追问 2：「等价类里的数据真的『等效』吗？有没有反例？」**

> 参考回答：等效是针对"揭露某类错误"而言，不是绝对等价，乱用会漏。经典反例：手机号输入框按"11 位数字"划等价类，选一个代表值——但如果校验还有号段白名单，138 开头有效而 199 拒绝，同一个等价类里出现两种结果，等效假设破产。所以实践里等价类划分前要先读清校验规则，按"程序对输入的真实处理路径"划分类别：规则里每多一个分支条件，等价类就要多切一刀。这也是等价类必须和判定表、错误推测法配合使用的原因。

**追问 3：「用例评审时别人质疑你的用例『太细、太多』，你怎么回应？」**

> 参考回答：先分清质疑来源再回应。如果来自开发（嫌多），我拿风险说事：涉及资金和数据的用例集是不可砍的基线，可协商的是低风险探索区，并给出"砍掉后漏测风险由谁承担"的明确结论。如果来自测试同行（嫌太细），我区分场景：冒烟和回归集要控制粒度保证可持续，探索性测试反而需要粗粒度 checklist。核心理由只有一条：用例数量本身不是目标，**风险覆盖才是**——评审的目标是就"为什么测这些"达成共识，而不是争论条数多少。
