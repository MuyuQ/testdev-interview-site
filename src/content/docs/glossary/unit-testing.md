## 一句话定义

单元测试是对软件中最小可测试单元（通常是函数或方法）进行验证的测试方法，在隔离环境下验证其行为是否符合预期。

## 为什么重要

- **快速反馈**：秒级执行，能快速发现逻辑错误，是CI/CD流水线的第一道防线
- **重构保障**：有单元测试覆盖的代码，重构时能快速发现破坏性改动
- **文档作用**：测试用例即活文档，展示函数的预期行为和边界条件
- **驱动设计**：写测试时发现难以测试的代码，往往意味着设计有问题（高耦合、职责不清）

## 工作流位置

```
需求分析 → 编码 → 【单元测试】 → 集成测试 → E2E测试 → 上线
                        ↑
                   开发者自测环节
```

单元测试是开发者自测的核心手段，在代码提交前执行，是测试金字塔的底层基础。

## 最小例子

```javascript
// 被测函数：计算两数之和
function add(a, b) {
  return a + b;
}

// 单元测试（使用 Jest）
describe('add函数', () => {
  it('应该返回两数之和', () => {
    expect(add(1, 2)).toBe(3);
  });

  it('应该处理负数', () => {
    expect(add(-1, 1)).toBe(0);
  });

  it('边界情况：0值', () => {
    expect(add(0, 0)).toBe(0);
  });
});
```

运行：`jest add.test.js`，几毫秒内得到结果。

## 面试怎么说

> "单元测试是对代码最小可测试单元的验证，核心是**隔离依赖**和**快速执行**。在实际项目中，我会为纯函数、工具方法、核心业务逻辑编写单元测试，使用Mock隔离数据库、API等外部依赖。我认为覆盖率是参考指标而非目标，关键在于覆盖核心路径和边界条件。单元测试帮我建立了重构信心，也是TDD实践的基础。"

## 易错点

1. **过度Mock**：连简单计算都Mock，测试失去意义。原则：能不Mock就不Mock。
2. **测试私有方法**：私有方法应通过公开方法间接测试，测试私有方法会导致测试与实现细节强耦合。
3. **断言不充分**：只调用函数不验证结果，或断言太宽泛（如`expect(result).toBeDefined()`）。
4. **依赖真实环境**：单元测试依赖数据库、网络会让测试变慢、不稳定，应使用Mock/Stub隔离。
5. **追求100%覆盖率**：为覆盖率写无意义测试，边际收益递减，核心业务覆盖好即可。

## 混淆概念

### 单元测试 vs 集成测试

| 维度 | 单元测试 | 集成测试 |
|------|---------|---------|
| 测试范围 | 单个函数/方法 | 多个模块协作 |
| 依赖处理 | Mock隔离外部依赖 | 使用真实依赖 |
| 执行速度 | 毫秒级 | 秒到分钟级 |
| 定位难度 | 精准到具体函数 | 需排查模块间交互 |
| 示例 | 测试`calculateTax()` | 测试订单创建→扣库存→支付 |

简单判断：**需要启动服务或连接外部资源的，通常是集成测试。**

### 代码覆盖率误区

代码覆盖率 = 被执行过的代码行 / 总代码行 × 100%

**常见误解**：
- ❌ "覆盖率80%意味着80%的质量" → 只代表执行过，不代表断言充分
- ❌ "100%覆盖率就没有bug" → 覆盖的是代码路径，不是业务场景组合
- ❌ "覆盖率越高越好" → 边际收益递减，追求100%会写无意义测试

**正确理解**：
- 覆盖率是**发现未测试代码**的工具，不是目标
- 关注**分支覆盖率**而非仅行覆盖率（if的true/false都测了吗？）
- 核心业务逻辑追求高覆盖，工具函数可适当放宽
