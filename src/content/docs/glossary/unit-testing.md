## 一句话定义

单元测试是对软件中**最小可测试单元**（通常是函数或方法）进行验证的测试方法，在**隔离环境**下验证其行为是否符合预期。

一句话抓住本质：单元测试 = 最小单元 + 隔离依赖 + 快速执行。它不关心数据库能不能连上、网络通不通，只关心"我这个函数给定输入，产出对不对"。

## 为什么重要

- **快速反馈**：秒级执行，能快速发现逻辑错误，是 CI/CD 流水线的第一道防线
- **重构保障**：有单元测试覆盖的代码，重构时能快速发现破坏性改动——这是"敢改代码"的底气来源
- **文档作用**：测试用例即活文档，展示函数的预期行为和边界条件，新成员读测试比读注释更快理解代码
- **驱动设计**：写测试时发现难以测试的代码，往往意味着设计有问题（高耦合、职责不清）。好的代码一定是"可测"的
- **降低缺陷成本**：单元测试能在最便宜的阶段（开发本地）拦住大部分逻辑错误，避免流到集成/系统/生产才被发现

## 它在真实工作流中的位置

```
需求分析 → 编码 → 【单元测试】 → 集成测试 → E2E测试 → 上线
                        ↑
                   开发者自测环节
```

单元测试是**开发者自测**的核心手段，在代码提交前执行，是测试金字塔的底层基础。一个健康项目里，单测数量应该占测试总量的 60%~70%。

## 写好单元测试的三个习惯

光知道定义不够，实战中三个习惯直接决定单测质量：

### 1. 遵循 AAA 模式（Arrange-Act-Assert）

每个测试用例都应清晰分成三段，阅读者一眼就能看出"准备什么、测什么、验证什么"：

```javascript
// 被测函数：计算两数之和
function add(a, b) {
  return a + b;
}

describe('add 函数', () => {
  it('应该返回两数之和', () => {
    // Arrange：准备输入与期望
    const a = 1, b = 2;
    const expected = 3;

    // Act：执行被测逻辑
    const result = add(a, b);

    // Assert：验证结果
    expect(result).toBe(expected);
  });
});
```

三段分离的好处是：当测试失败时，你能立刻定位是"准备错了""逻辑算错了"还是"断言写错了"。

### 2. 测试命名要"自解释"

坏命名：`test1`、`testAdd`。好命名直接描述场景和期望：

```javascript
it('add(负数, 正数) 应正确返回两者之和', () => { /* ... */ });
it('add(0, 0) 边界值应返回 0', () => { /* ... */ });
```

命名建议公式：`[被测对象] 在 [场景/输入] 下，应 [期望结果]`。这样测试报告本身就是一份需求清单。

### 3. 善用参数化，避免重复用例

当多个用例只是输入不同，用参数化一次表达，比复制粘贴 10 个 `it` 更清晰、更好维护：

```javascript
// Jest 参数化示例：一个用例覆盖多组输入
test.each([
  [1, 2, 3],
  [-1, 1, 0],
  [0, 0, 0],
  [100, -100, 0],
])('add(%i, %i) 应返回 %i', (a, b, expected) => {
  expect(add(a, b)).toBe(expected);
});
```

## 最小例子（带 setup/teardown）

真实项目里，单测常需要准备环境（如建临时数据库、mock 外部服务）。用框架的 setup/teardown 把"准备"和"清理"收口，不让它们污染每个用例：

```javascript
// 使用 Jest 的 beforeEach/afterEach 管理测试上下文
describe('购物车计算', () => {
  let cart;

  beforeEach(() => {
    // 每个用例前准备一个干净的购物车
    cart = createCart();
  });

  afterEach(() => {
    // 每个用例后清理，保证用例之间互不干扰（测试隔离）
    cart.clear();
  });

  it('空购物车总价为 0', () => {
    expect(cart.total()).toBe(0);
  });

  it('加入商品后总价正确累加', () => {
    cart.add({ price: 10, quantity: 2 });
    expect(cart.total()).toBe(20);
  });
});
```

这里 `beforeEach`/`afterEach` 保证了**测试隔离**——每个用例都从干净状态开始，失败也不会互相牵连。这是单测能稳定、可重复执行的前提。

## 单元测试与测试替身

单元测试要"隔离"，就意味着外部依赖（数据库、网络、第三方 API、文件系统）要被替身（Test Double）替换掉。常见四类：

| 替身 | 作用 | 单测中何时用 |
|------|------|-------------|
| **Stub** | 提供预设返回值 | 被测逻辑依赖某外部数据（如查用户）时，直接给假数据 |
| **Mock** | 验证是否被正确调用 | 验证"发没发邮件""调没调支付"这类行为交互 |
| **Fake** | 简化版真实实现 | 用内存数据库代替真实 MySQL，又快又真 |
| **Spy** | 包装真实对象记录调用 | 想知道真实对象被调了几次，但不改变其行为 |

细节可参考 [Mock/Stub](/testdev-interview-site/glossary/mock-stub/)。原则是：**能不 mock 就不 mock**，纯逻辑优先用真实代码，只在隔离外部依赖时使用替身。

## 面试怎么说

> "单元测试是对代码最小可测试单元的验证，核心是**隔离依赖**和**快速执行**。在实际项目中，我会为纯函数、工具方法、核心业务逻辑编写单元测试，使用 Mock 隔离数据库、API 等外部依赖。我习惯用 AAA 模式组织用例，用参数化减少重复。
>
> 我认为覆盖率是参考指标而非目标，关键在于覆盖核心路径和边界条件。单元测试帮我建立了重构信心，也是 TDD 实践的基础——先写失败测试，再写实现让它变绿，最后重构。"

如果追问 TDD：TDD 是"红-绿-重构"循环——先写一个会失败的测试（红），写最少代码让它通过（绿），再在测试保护下优化实现（重构）。单测就是这套循环的基石。

## 易错点

1. **过度 Mock**：连简单计算都 Mock，测试失去意义。原则：能不 Mock 就不 Mock。
2. **测试私有方法**：私有方法应通过公开方法间接测试，测试私有方法会导致测试与实现细节强耦合。
3. **断言不充分**：只调用函数不验证结果，或断言太宽泛（如 `expect(result).toBeDefined()`），等于没测。
4. **依赖真实环境**：单元测试依赖数据库、网络会让测试变慢、不稳定，应使用 Mock/Stub 隔离。
5. **追求 100% 覆盖率**：为覆盖率写无意义测试，边际收益递减，核心业务覆盖好即可。
6. **用例间互相依赖**：上一个用例的结果影响下一个，导致"单独跑挂、一起跑过"的诡异现象。每个用例必须独立可运行。
7. **忽略测试可读性**：测试也是代码，一团乱麻的测试将来没人敢改，最终被删掉，覆盖随之流失。

## 容易混淆的概念

### 单元测试 vs 集成测试

| 维度 | 单元测试 | 集成测试 |
|------|---------|---------|
| 测试范围 | 单个函数/方法 | 多个模块协作 |
| 依赖处理 | Mock 隔离外部依赖 | 使用真实依赖 |
| 执行速度 | 毫秒级 | 秒到分钟级 |
| 定位难度 | 精准到具体函数 | 需排查模块间交互 |
| 示例 | 测试 `calculateTax()` | 测试订单创建→扣库存→支付 |

简单判断：**需要启动服务或连接外部资源的，通常是集成测试。**

### 代码覆盖率误区

代码覆盖率 = 被执行过的代码行 / 总代码行 × 100%

**常见误解**：
- ❌ "覆盖率 80% 意味着 80% 的质量" → 只代表执行过，不代表断言充分
- ❌ "100% 覆盖率就没有 bug" → 覆盖的是代码路径，不是业务场景组合
- ❌ "覆盖率越高越好" → 边际收益递减，追求 100% 会写无意义测试

**正确理解**：
- 覆盖率是**发现未测试代码**的工具，不是目标
- 关注**分支覆盖率**而非仅行覆盖率（if 的 true/false 都测了吗？）
- 核心业务逻辑追求高覆盖，工具函数可适当放宽

## 自测题

1. 你项目的单元测试覆盖率是多少？你觉得够吗？

2. 你是如何隔离外部依赖的？用的什么 Mock 策略？

3. 能举例说明一次单元测试帮你避免了线上 bug 吗？

4. 当测试与实现细节强耦合时，会带来什么问题？

5. **场景题**：下面这个测试有什么问题？

   ```javascript
   it('测试登录', () => {
     const user = login('admin', '123456');
     expect(user).toBeDefined();
   });
   ```

   <details>
   <summary>点击查看答案</summary>

   断言太弱：`toBeDefined()` 只验证了"返回了东西"，没验证登录到底成没成功、返回的是不是正确的用户。如果 `login` 永远返回 `{}`，这个测试也会绿，但其实是假的通过。应断言关键字段，例如 `expect(user.username).toBe('admin')`、`expect(user.token).toBeTruthy()`。这就是"断言不充分"的典型易错点。
   </details>
