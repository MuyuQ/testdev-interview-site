## 追问链概览

电商订单是面试高频考点，面试官往往从订单流程切入，层层追问幂等性、并发、状态机等深水区。本追问链帮助你系统准备，从容应对。

**首问问题**：说说电商订单的完整流程是怎样的？

**追问层级**：首问 → 订单创建 → 支付回调 → 幂等性设计 → 并发扣减 → 状态机 → 异常处理

---

## 第一层：首问回答策略

### 面试官意图

考察你对电商业务的系统性理解，是否能从用户视角完整描述业务链路，而非只关注技术细节。

### 推荐回答框架

```text
电商订单的完整流程可以分为六个阶段：

第一阶段是商品浏览。用户在首页或分类页浏览商品，通过搜索或推荐找到目标商品，
查看商品详情包括规格、价格、库存信息。

第二阶段是购物车操作。用户选择商品规格后加入购物车，购物车服务校验库存
并计算优惠价格，用户可以修改数量或删除商品。

第三阶段是订单创建。用户提交订单后，系统校验库存可用性和价格有效性，
生成订单号并创建订单记录，状态为待支付，同时预扣库存并设置15分钟支付超时。

第四阶段是支付流程。用户选择支付方式后跳转支付网关，完成支付后网关回调
通知结果，系统更新订单状态为已支付并触发发货流程。

第五阶段是发货履约。订单推送至仓储系统生成发货单，仓库拣货打包后物流揽收，
用户可以查询物流轨迹。

第六阶段是订单完成。用户确认收货或系统自动确认后，订单状态变更为已完成，
触发积分发放和评价提醒。
```

### 回答要点

| 要点 | 阐述方式 | 追问风险 |
|------|----------|----------|
| 用户视角 | 从用户操作角度描述 | 低 |
| 服务交互 | 自然穿插服务职责说明 | 中 |
| 异常提及 | 概括说明有超时取消等机制 | 高（追问异常处理） |

## 第二层追问：订单创建细节

### 追问问题

订单创建时做了哪些校验？

### 面试官意图

考察对订单创建业务逻辑的理解深度，是否只知道"创建订单"而不懂内部校验机制。

### 强回答

```text
订单创建时我们做了三层校验：

第一层是库存校验。调用库存服务检查商品是否有足够库存，如果库存不足直接
拒绝下单并返回提示信息。库存校验通过后会预扣库存，防止下单后库存被其他
用户抢走。

第二层是价格校验。重新计算商品价格、优惠金额、运费，校验前端传来的价格
是否与后端计算一致。这一步防止前端篡改价格导致的资金损失，比如用户把
100元的商品改成1元提交。

第三层是用户状态校验。检查用户账号是否正常、是否有下单权限、收货地址
是否有效。对于新用户可能还需要检查实名认证状态。

校验全部通过后，生成全局唯一的订单号，创建订单记录，设置初始状态为
待支付，同时写入订单商品明细表和订单日志表。
```

### 弱回答

```text
订单创建就是调用接口传参数，然后数据库插入一条记录，返回订单号。
```

### 补救方式

如果只给出了弱回答，面试官追问"库存不够会发生什么"，可以补救：

```text
库存不够的话会直接拒绝下单，返回库存不足的错误提示。我们系统里有库存
预扣机制，下单时先锁定库存，支付成功才真正扣减，超时未支付会释放库存。
```

## 第三层追问：支付回调处理

### 追问问题

支付成功后回调是怎么处理的？

### 面试官意图

这是深水区问题，考察对支付回调机制的理解，特别是幂等性处理。

### 强回答

```text
支付回调的处理流程我分四步说明：

第一步是接收回调。支付网关会向我们的回调接口发送支付结果通知，包含
订单号、支付金额、交易流水号、支付状态等信息。

第二步是签名校验。我们用支付网关的公钥验证回调签名，确保回调是真实
的而非伪造攻击。签名校验失败会拒绝处理并记录安全日志。

第三步是幂等处理。这是最关键的一步。支付网关可能多次发送同一笔支付
的回调通知，我们必须保证只处理一次。我们用订单号+支付流水号作为唯一键，
查询数据库是否已处理过，如果已处理则直接返回成功响应不再重复操作。

第四步是状态更新。确认是首次处理后，更新订单状态为已支付，写入支付
流水记录，触发发货流程。同时发送支付成功通知给用户，比如短信或APP推送。

整个流程中，如果处理失败我们会返回特定错误码，支付网关会按策略重试，
最终如果持续失败，我们有定时任务主动查询支付结果进行补偿处理。
```

### 弱回答

```text
支付成功后支付平台会通知我们，我们收到通知就更新订单状态。
```

### 补救方式

如果弱回答后被追问"支付平台多次通知怎么办"，可以补救：

```text
支付平台可能会重发通知，所以我们有幂等校验，同一笔支付不会重复处理。
具体的做法是用支付流水号查数据库，已经处理过的直接返回成功。
```

## 第四层追问：幂等性设计

### 追问问题

幂等性具体是怎么实现的？

### 面试官意图

深入考察幂等性技术实现，这是支付场景的核心考点。

### 强回答

```text
我们用三层机制保证幂等性：

第一层是数据库唯一索引。支付流水表有订单号+支付流水号的联合唯一索引，
同一笔支付重复写入会报唯一索引冲突，数据库层面就阻止了重复记录。

第二层是分布式锁。在处理回调前，先基于订单号获取分布式锁，保证同一
订单的回调串行处理。获取锁失败说明有其他线程正在处理，当前请求等待
或直接返回。

第三层是状态校验。查询订单当前状态，如果已经是已支付状态，说明已处理
过，直接返回成功响应。状态校验是最轻量的幂等判断，通常作为第一道防线。

实际代码流程是：先查订单状态，已支付直接返回；未支付则获取分布式锁，
再次查状态确认，然后执行支付处理逻辑，最后释放锁。
```

### 弱回答

```text
幂等就是加个锁，或者查一下有没有处理过。
```

### 补救方式

追问"加什么锁"时可以补救：

```text
我们用的是Redis分布式锁，因为服务是多实例部署，Java的本地锁没法跨实例
互斥。锁的key是订单号，处理完释放锁。为了防止死锁我们还设置了锁过期时间。
```

## 第五层追问：并发库存扣减

### 追问问题

高并发时库存扣减怎么保证正确性？

### 非试官意图

考察并发场景下的数据一致性保障，这是电商测试的核心难点。

### 强回答

```text
高并发库存扣减我们用双重保障机制：

第一重是Redis预扣。下单时不直接扣数据库库存，而是先扣Redis中的库存
计数器。Redis是单线程操作，天然保证原子性，不会出现超扣。扣减成功才
允许下单，扣减失败直接返回库存不足。

第二重是数据库乐观锁。支付成功后真正扣数据库库存时，使用乐观锁机制。
库存表有version字段，扣减时带上version条件，UPDATE时version不匹配
说明有并发修改，扣减失败触发重试或补偿。

两层机制配合，Redis预扣挡住大部分并发请求，数据库乐观锁兜底保证
最终一致性。同时有定时任务同步Redis和数据库库存，处理可能的偏差。

测试时我专门做了并发扣减压测，用JMeter模拟100并发购买同一商品，
验证库存不会出现负数，也不会超卖或少卖。
```

### 弱回答

```text
高并发时加锁就行了，锁住库存不让其他人操作。
```

### 补救方式

追问"加什么锁，怎么测试"时可以补救：

```text
我们用的是Redis分布式锁加数据库乐观锁。测试时我用压测工具模拟并发
购买，检查扣减后的库存数量是否正确，有没有超卖情况。
```

## 更深一层追问：订单状态机

### 追问问题

订单状态是怎么设计的？

### 非试官意图

考察状态机设计理解，这是订单系统的核心架构。

### 强回答

```text
订单状态机我们设计了十几种状态，核心状态有：待支付、已支付、待发货、
已发货、待收货、已完成、已取消、已退款。

状态流转规则我们用状态机模式严格控制：
- 待支付只能流转到已支付（支付成功）或已取消（超时或用户取消）
- 已支付只能流转到待发货（发货准备）或已退款（申请退款）
- 待发货只能流转到已发货（物流揽收）
- 已发货只能流转到待收货（物流送达）或已退款（退货）
- 待收货只能流转到已完成（用户确认）或已退款（退货）

不允许非法流转，比如已取消的订单不能直接变成已发货。每个状态变更
都写入订单日志表，记录变更时间、操作人、变更原因。

测试时我专门设计了状态机测试用例，验证每个状态只能按规则流转，
非法流转会被拒绝并返回错误提示。
```

### 弱回答

```text
订单有待支付、已支付、已发货、已完成这些状态。
```

## 演练方法

### 自我演练步骤

1. 首问计时练习：用 2-3 分钟完整叙述订单流程，录音检查是否遗漏关键环节
2. 追问压力练习：让朋友或同事模拟追问，尝试打断回答，训练抗压能力
3. 补洞自查：对照追问链检查自己的薄弱点，针对性补学习

### 模拟面试脚本

```text
面试官：说说电商订单的完整流程
→ [回答首问，控制在2-3分钟]

面试官：订单创建时做了哪些校验？
→ [回答三层校验，重点讲库存和价格]

面试官：支付回调怎么处理的？
→ [重点讲幂等性，四步流程]

面试官：幂等性具体怎么实现？
→ [三层机制：唯一索引、分布式锁、状态校验]

面试官：高并发库存扣减怎么保证正确性？
→ [双重保障：Redis预扣 + 数据库乐观锁]

面试官：订单状态是怎么设计的？
→ [讲核心状态和流转规则，强调非法流转保护]
```

### 验收标准

完成演练后，检查是否达到：
- 能流畅回答首问，不遗漏核心环节
- 幂等性回答有具体实现细节（至少两层机制）
- 并发扣减回答有测试验证部分
- 状态机回答有流转规则而非只列举状态
- 每个追问都能给出补救思路
