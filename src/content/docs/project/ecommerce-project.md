## 1. 项目背景

### 业务目标

电商项目是一个面向C端用户的大型在线购物平台，日均订单量50万+，峰值QPS可达3000。平台核心业务目标包括：

- **用户增长**：通过优质购物体验提升用户留存率和复购率
- **交易转化**：优化下单支付流程，降低订单流失率
- **供应链效率**：整合仓储物流，实现高效履约
- **平台收益**：通过营销活动和会员体系提升GMV

### 用户群体

- **C端用户**：普通消费者，日活100万+，关注购物体验、支付安全、物流时效
- **B端商家**：入驻商户，关注商品管理、订单处理、结算对账
- **运营人员**：平台运营团队，关注活动配置、数据分析、客服支持
- **仓储物流**：仓库管理员、配送人员，关注库存管理、发货调度

### 核心链路

电商系统的核心链路是「浏览 → 加购 → 下单 → 支付 → 发货 → 收货」，每个环节都有独立的服务支撑，通过微服务架构协同工作。

```
用户端                    服务端                      外部系统
  │                         │                          │
  ├─ 浏览商品 ───────────→ 商品服务                    │
  ├─ 加入购物车 ─────────→ 购物车服务                   │
  ├─ 提交订单 ───────────→ 订单服务 ──────────────→ 库存服务
  ├─ 发起支付 ───────────→ 支付服务 ──────────────→ 支付网关
  ├─ 支付回调 ───────────→ 支付服务 ──────────────→ 消息队列
  │                         ↓                          │
  │                    订单状态更新                       │
  │                         ↓                          │
  └─ 物流跟踪 ←───────── 物流服务 ←─────────────── 物流商
```

## 3. 业务流程

### 主流程：用户下单全链路

1. **商品浏览**
   - 用户进入首页/分类页，系统推荐商品
   - 用户搜索商品，ES检索返回结果
   - 用户查看商品详情，包括规格、库存、价格

2. **购物车操作**
   - 用户选择商品规格，加入购物车
   - 购物车服务校验库存、计算优惠
   - 用户修改数量、删除商品

3. **订单创建**
   - 用户提交订单，系统校验库存、价格、优惠
   - 生成订单号，创建订单记录（状态：待支付）
   - 预扣库存，设置支付超时时间（15分钟）

4. **支付流程**
   - 用户选择支付方式（微信/支付宝/银行卡）
   - 跳转支付网关，用户完成支付
   - 支付网关回调通知支付结果
   - 系统更新订单状态（已支付），触发发货流程

5. **发货履约**
   - 订单推送至WMS系统，生成发货单
   - 仓库拣货打包，物流公司揽收
   - 用户查询物流轨迹

6. **订单完成**
   - 用户确认收货或系统自动确认（7天）
   - 订单状态变更为已完成
   - 触发积分发放、评价提醒

### 异常流程

- **库存不足**：下单时库存不足，提示用户并推荐相似商品
- **支付超时**：15分钟未支付，订单自动取消，释放库存
- **支付失败**：支付网关返回失败，订单状态回滚，允许重新支付
- **发货异常**：物流停滞或丢件，触发客服介入流程

## 4. 质量风险

### 高风险节点

| 风险等级 | 环节     | 风险描述                     | 影响范围           |
| -------- | -------- | ---------------------------- | ------------------ |
| P0       | 支付回调 | 回调丢失导致订单状态不一致   | 资金损失、用户投诉 |
| P0       | 库存扣减 | 超卖或少卖                   | 资金损失、信誉受损 |
| P0       | 价格计算 | 优惠叠加计算错误             | 资金损失、用户投诉 |
| P1       | 订单创建 | 高并发下订单重复创建         | 重复发货、库存异常 |
| P1       | 支付超时 | 定时任务失效导致订单无法取消 | 库存积压           |
| P2       | 搜索服务 | ES索引延迟或数据不一致       | 用户搜索体验差     |

### 风险点详解

**支付回调幂等性风险**

- 问题：支付网关可能多次发送回调通知
- 影响：重复处理导致订单状态异常、重复发货
- 方案：基于订单号+支付流水号实现幂等校验

**库存并发扣减风险**

- 问题：高并发下多个请求同时扣减同一商品库存
- 影响：超卖导致无法发货、用户投诉
- 方案：Redis分布式锁 + 数据库乐观锁双重保障

**价格计算精度风险**

- 问题：浮点数计算精度丢失
- 影响：订单金额与实际支付金额不一致
- 方案：使用BigDecimal进行金额计算，统一保留2位小数

## 8. 故障和复盘

### 典型故障案例

**案例一：支付回调丢失**

- **现象**：用户支付成功，但订单状态仍为待支付
- **定位过程**：
  1. 查询支付网关日志，确认回调已发送
  2. 检查应用日志，发现回调接口偶发超时
  3. 分析原因：支付网关重试机制配置错误，重试间隔过短导致服务雪崩
- **解决方案**：
  1. 增加消息队列缓冲，异步处理回调
  2. 完善幂等机制，支持重复回调安全处理
  3. 增加主动查询补偿机制
- **测试改进**：增加支付回调丢失场景的自动化用例

**案例二：库存超卖**

- **现象**：商品库存为0，但仍能下单成功
- **定位过程**：
  1. 分析订单数据，发现同一时刻多个订单扣减同一商品
  2. 检查库存服务日志，发现并发扣减时未加锁
  3. 压测复现：100并发请求，库存出现负数
- **解决方案**：
  1. 引入Redis分布式锁
  2. 数据库层面增加乐观锁（version字段）
  3. 库存预扣+最终扣减分离
- **测试改进**：增加并发扣减库存的专项测试

### 复盘机制

每次线上故障后，组织复盘会议，输出：

1. **根因分析**：5Why分析法找到根本原因
2. **改进措施**：技术改进 + 流程改进
3. **测试补充**：补充测试用例、自动化覆盖
4. **文档沉淀**：更新知识库，避免同类问题

## 10. 可能追问

### 技术类追问

1. **支付幂等性怎么测试？**
   - 设计重复回调用例，验证订单状态不会重复更新
   - 模拟并发回调，验证不会重复发货
   - 验证数据库唯一索引约束有效性

2. **库存并发扣减怎么保证正确性？**
   - 使用JMeter进行并发压测
   - 验证Redis锁的获取和释放
   - 验证乐观锁version字段更新

### 刁钻追问与参考回答

下面这组追问比上面两类更"往人身上扎"，重点考察你是不是真的做过。回答时要带细节，细节编不出来就说明没做过。

**追问1：500 多个接口用例，测试数据是怎么造的？总不能每次手工准备吧？**

参考回答：分三层。第一层是账号类基础数据，跑批前通过注册接口预热到账号池，按并行进程分配独占账号；第二层是业务单据类数据，用数据工厂现造现用——比如要测「已支付订单」，就现场走一遍下单加 Mock 支付成功，用完标记废弃，保证用例之间零依赖；第三层是极难构造的状态（比如超时关单后的库存回滚），直连测试库改状态位，但改完会通过业务接口再查一遍，确认系统侧视图一致。核心原则：能用接口造的不用 SQL，能现造的不用共享的，避免用例互相踩。

**追问2：开发自己也自测，你的接口自动化和开发自测的区别是什么？**

参考回答：三个区别。第一，断言深度不同：开发自测看到返回 200 就算过，我的用例是接口返回、数据库落库、下游消息三层断言，比如下单用例会再查库存服务的预扣记录；第二，场景侧重不同：开发自测偏向「正常能跑通」，我的用例集里异常和边界场景占一半以上，金额 0.01、参数缺失、并发回调这些开发很少自己碰；第三，生命周期不同：开发自测是一次性的，我的用例进 CI 每次提交都跑，价值在防回归——之前一个迭代里约三成的回归问题是在提测前被这套用例拦下来的（示例数字，请替换成你的真实数据）。

**追问3：为什么框架要拆成配置层、封装层、用例层？写一个文件里不是更快？**

参考回答：用例少的时候单文件确实快，但我们是多环境（DEV/SIT/UAT）加多人协作，分层的收益体现在变更成本上：切环境只改配置文件，用例一行不动；登录、签名这些公共逻辑收敛在封装层，接口改版只改一处；用例层只剩业务描述，新人第一天就能照着写。分层过度我也警惕：如果加一个用例要同时改三个文件，那就是分层过度，我们的应对是把常用组合下沉成 Fixture。可以参考 [Fixture 策略](/testdev-interview-site/coding/fixture-strategy/) 的思路。

**追问4：支付回调依赖第三方，测试环境里怎么模拟「回调丢失」？**

参考回答：自建支付网关 Mock，按订单号前缀路由剧本：以 `LOST_` 开头的单直接吞掉回调不响应，以 `RETRY_` 开头的先超时、30 秒后补发一次。被测系统切到 Mock 模式只改渠道网关地址这一个配置，其他逻辑不动，这样测出来的补偿行为才可信。框架里 [重试机制](/testdev-interview-site/coding/retry-mechanism/) 的验证也是同一套思路。真实联调阶段再用渠道沙箱把关键场景复核一遍，Mock 和沙箱的职责是分开的。

## 项目难点与解决

以下数字均为示例，讲之前请替换成你自己的真实数据。

### 难点一：测试环境数据互相污染，用例经常"莫名失败"

**问题**：SIT 环境多人共用，自动化跑到一半商品库存被别人改了、订单被手工关掉，用例失败率一度接近 20%，失败排查时间比写用例还长，没人再信 CI 红灯。

**分析**：拉一个月的失败用例日志归类，约七成失败和用例逻辑无关，全是共享数据被并发修改导致前置状态失效。根因是「用例依赖固定数据」：所有用例都用同一个测试商品、同一个测试账号。

**方案**：三步走。第一，数据工厂改成现造现用，每个用例创建自己的商品和订单，用完标记废弃；第二，账号池隔离，每个并行任务独占账号，避免登录态互踢；第三，执行前增加环境探活和数据预检，前置条件不满足直接标记「环境跳过」，不计入用例失败。

**结果**：非代码原因的失败从七成降到一成以内，整体失败率稳定在 3% 以下，CI 红灯重新有了公信力，团队才敢拿它当提测门禁。

### 难点二：UI 自动化太脆，没人敢动

**问题**：核心路径 UI 用例 50 多条，前端改一版就挂一半，维护成本高到没人愿意认领。

**分析**：复盘失败原因，大头是定位策略不稳定（早期用了 XPath 绝对路径）和固定 sleep 导致的时序问题，小头是页面结构真变了但没人及时更新脚本。参考 [页面对象模式](/testdev-interview-site/glossary/page-object-pattern/) 重构了定位层。

**方案**：定位统一收敛到 data-testid，和前端约定「测试属性必填」；等待全部改成显式等待，封装统一的元素操作入口；每条 UI 用例标注意图，连续两周失败的用例直接下线重写，不允许带病重试。

**结果**：UI 用例稳定性从约 70% 提升到 95% 以上，单次前端发版后的脚本修复时间从半天降到半小时内。

### 难点三：全量回归一次 2 小时，流水线成了瓶颈

**问题**：迭代后期接口用例涨到 500+，全量回归接近 2 小时，开发合并后经常排队等结果，开始有人绕过 CI 直接合并。

**分析**：用 pytest 打点统计耗时，瓶颈有三个：用例串行执行、每个用例都重新登录、部分用例里写死了 sleep。

**方案**：接入 pytest-xdist 多进程并行，按模块拆分并配合难点一的账号池保证数据不冲突；登录态做成 session 级 Fixture，一个进程只登录一次；逐个替换固定 sleep 为轮询等待。流水线拆成两级：冒烟由提交触发、10 分钟内出结果，全量每日凌晨跑。

**结果**：全量回归从约 2 小时压到 40 分钟，冒烟稳定在 10 分钟内，绕过 CI 的情况基本消失。
