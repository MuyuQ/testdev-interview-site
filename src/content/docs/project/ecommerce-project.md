## 1. 项目背景

### 业务目标

电商项目是一个面向C端用户的大型在线购物平台，日均订单量50万+，峰值QPS可达3000。平台核心业务目标包括：

- **用户增长**：通过优质购物体验提升用户留存率和复购率
- **交易转化**：优化下单支付流程，降低订单流失率
- **供应链效率**：整合仓储物流，实现高效履约
- **平台收益**：通过营销活动和会员体系提升GMV

### 用户群体

- **C端用户**：普通消费者，日活100万+，关注购物体验、支付安全、物流时效
- **B端商家**：入驻商户，关注商品管理、订单处理、结算对账
- **运营人员**：平台运营团队，关注活动配置、数据分析、客服支持
- **仓储物流**：仓库管理员、配送人员，关注库存管理、发货调度

### 核心链路

电商系统的核心链路是「浏览 → 加购 → 下单 → 支付 → 发货 → 收货」，每个环节都有独立的服务支撑，通过微服务架构协同工作。

```
用户端                    服务端                      外部系统
  │                         │                          │
  ├─ 浏览商品 ───────────→ 商品服务                    │
  ├─ 加入购物车 ─────────→ 购物车服务                   │
  ├─ 提交订单 ───────────→ 订单服务 ──────────────→ 库存服务
  ├─ 发起支付 ───────────→ 支付服务 ──────────────→ 支付网关
  ├─ 支付回调 ───────────→ 支付服务 ──────────────→ 消息队列
  │                         ↓                          │
  │                    订单状态更新                       │
  │                         ↓                          │
  └─ 物流跟踪 ←───────── 物流服务 ←─────────────── 物流商
```

## 3. 业务流程

### 主流程：用户下单全链路

1. **商品浏览**
   - 用户进入首页/分类页，系统推荐商品
   - 用户搜索商品，ES检索返回结果
   - 用户查看商品详情，包括规格、库存、价格

2. **购物车操作**
   - 用户选择商品规格，加入购物车
   - 购物车服务校验库存、计算优惠
   - 用户修改数量、删除商品

3. **订单创建**
   - 用户提交订单，系统校验库存、价格、优惠
   - 生成订单号，创建订单记录（状态：待支付）
   - 预扣库存，设置支付超时时间（15分钟）

4. **支付流程**
   - 用户选择支付方式（微信/支付宝/银行卡）
   - 跳转支付网关，用户完成支付
   - 支付网关回调通知支付结果
   - 系统更新订单状态（已支付），触发发货流程

5. **发货履约**
   - 订单推送至WMS系统，生成发货单
   - 仓库拣货打包，物流公司揽收
   - 用户查询物流轨迹

6. **订单完成**
   - 用户确认收货或系统自动确认（7天）
   - 订单状态变更为已完成
   - 触发积分发放、评价提醒

### 异常流程

- **库存不足**：下单时库存不足，提示用户并推荐相似商品
- **支付超时**：15分钟未支付，订单自动取消，释放库存
- **支付失败**：支付网关返回失败，订单状态回滚，允许重新支付
- **发货异常**：物流停滞或丢件，触发客服介入流程

## 4. 质量风险

### 高风险节点

| 风险等级 | 环节 | 风险描述 | 影响范围 |
|---------|------|----------|----------|
| P0 | 支付回调 | 回调丢失导致订单状态不一致 | 资金损失、用户投诉 |
| P0 | 库存扣减 | 超卖或少卖 | 资金损失、信誉受损 |
| P0 | 价格计算 | 优惠叠加计算错误 | 资金损失、用户投诉 |
| P1 | 订单创建 | 高并发下订单重复创建 | 重复发货、库存异常 |
| P1 | 支付超时 | 定时任务失效导致订单无法取消 | 库存积压 |
| P2 | 搜索服务 | ES索引延迟或数据不一致 | 用户搜索体验差 |

### 风险点详解

**支付回调幂等性风险**
- 问题：支付网关可能多次发送回调通知
- 影响：重复处理导致订单状态异常、重复发货
- 方案：基于订单号+支付流水号实现幂等校验

**库存并发扣减风险**
- 问题：高并发下多个请求同时扣减同一商品库存
- 影响：超卖导致无法发货、用户投诉
- 方案：Redis分布式锁 + 数据库乐观锁双重保障

**价格计算精度风险**
- 问题：浮点数计算精度丢失
- 影响：订单金额与实际支付金额不一致
- 方案：使用BigDecimal进行金额计算，统一保留2位小数

## 8. 故障和复盘

### 典型故障案例

**案例一：支付回调丢失**

- **现象**：用户支付成功，但订单状态仍为待支付
- **定位过程**：
  1. 查询支付网关日志，确认回调已发送
  2. 检查应用日志，发现回调接口偶发超时
  3. 分析原因：支付网关重试机制配置错误，重试间隔过短导致服务雪崩
- **解决方案**：
  1. 增加消息队列缓冲，异步处理回调
  2. 完善幂等机制，支持重复回调安全处理
  3. 增加主动查询补偿机制
- **测试改进**：增加支付回调丢失场景的自动化用例

**案例二：库存超卖**

- **现象**：商品库存为0，但仍能下单成功
- **定位过程**：
  1. 分析订单数据，发现同一时刻多个订单扣减同一商品
  2. 检查库存服务日志，发现并发扣减时未加锁
  3. 压测复现：100并发请求，库存出现负数
- **解决方案**：
  1. 引入Redis分布式锁
  2. 数据库层面增加乐观锁（version字段）
  3. 库存预扣+最终扣减分离
- **测试改进**：增加并发扣减库存的专项测试

### 复盘机制

每次线上故障后，组织复盘会议，输出：

1. **根因分析**：5Why分析法找到根本原因
2. **改进措施**：技术改进 + 流程改进
3. **测试补充**：补充测试用例、自动化覆盖
4. **文档沉淀**：更新知识库，避免同类问题

## 10. 可能追问

### 技术类追问

1. **支付幂等性怎么测试？**
   - 设计重复回调用例，验证订单状态不会重复更新
   - 模拟并发回调，验证不会重复发货
   - 验证数据库唯一索引约束有效性

2. **库存并发扣减怎么保证正确性？**
   - 使用JMeter进行并发压测
   - 验证Redis锁的获取和释放
   - 验证乐观锁version字段更新
   - 检查数据库库存扣减后的准确性

3. **自动化框架怎么处理测试数据？**
   - 使用工厂模式构造测试数据
   - 每个测试用例独立数据域，避免相互影响
   - 测试前准备数据，测试后清理数据
   - 使用Fixture实现数据生命周期管理

4. **怎么保证接口测试的覆盖率？**
   - 基于接口文档生成用例骨架
   - 覆盖正向、异常、边界场景
   - 使用JaCoCo统计代码覆盖率
   - 定期review覆盖率报告，补充遗漏场景

### 业务类追问

1. **电商项目的业务难点在哪？**
   - 状态机复杂：订单有多达十几种状态流转
   - 价格计算复杂：优惠叠加、满减、会员价
   - 数据一致性要求高：库存、订单、支付三者强一致

2. **怎么理解测试开发的价值？**
   - 提前发现问题，降低修复成本
   - 自动化回归，保障迭代效率
   - 质量体系建设，提升团队质量意识

## 11. 关联场景和技术

### 关联场景

- **秒杀场景**：高并发下的库存扣减、订单创建测试
- **大促场景**：流量激增下的系统稳定性验证
- **退款场景**：支付原路退回、库存回滚测试
- **多端同步**：APP、小程序、HB端数据一致性

### 关联技术

| 技术领域 | 应用场景 | 测试重点 |
|----------|----------|----------|
| 消息队列 | 订单状态流转、异步通知 | 消息可靠性、顺序性、幂等消费 |
| 分布式事务 | 订单-库存-支付一致性 | 最终一致性、补偿机制 |
| 缓存 | 商品信息、库存缓存 | 缓存一致性、穿透、雪崩 |
| 搜索引擎 | 商品搜索 | 搜索相关性、索引延迟 |
| 容器化 | 服务部署 | 部署一致性、服务发现 |
