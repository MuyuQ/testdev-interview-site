## 项目背景

### 先说结论

移动端测试比后台复杂得多：你面对的不是一台机器，而是**上千种设备组合 + 两套操作系统 + 随时断网的真实环境**。难点不在功能，而在「碎片化、弱网、状态流转、性能」这四座大山。

### 业务全景

某电商公司移动端 App，支持 iOS 和 Android 双平台，月活用户超过 500 万。双周迭代，每次发版涉及功能迭代、性能优化、体验改进。测试团队需在有限时间内保障版本质量，支撑业务快速增长。

**项目特点：**

- 双平台同步开发，测试工作量翻倍
- 设备碎片化严重，Android 机型超 300 款
- 涉及支付、订单等核心业务，质量要求高
- 需支持离线模式与弱网环境

### 测试四象限

| 象限       | 典型问题             | 测试手段          |
| ---------- | -------------------- | ----------------- |
| 功能正确性 | 下单失败、状态错乱   | 用例 + 接口自动化 |
| 兼容性     | 某机型白屏、按钮错位 | 云测 + 真机矩阵   |
| 稳定性     | 崩溃、ANR、卡死      | 专项 + 长稳测试   |
| 性能体验   | 启动慢、发热、耗电   | 性能采集 + 对比   |

## 测试开发角色

**测试负责人**：制定策略、资源调配、风险把控、跨部门协调。

**功能测试工程师**：执行功能用例、缺陷提交与跟踪、业务回归验证。

**自动化测试工程师**：搭建自动化框架、编写维护脚本、CI/CD 集成。

**性能测试工程师**：性能指标监控、瓶颈分析、优化建议。

**兼容性测试工程师**：机型适配、云测平台管理、问题归因。

> 我在项目中以**自动化 + 专项**为主责：搭 Appium 框架、做兼容矩阵、压性能、复现弱网支付问题。功能执行由功能同学负责，我不直接扛手工回归量。

## 业务流程

### 测试生命周期

```
需求评审 → 测试设计 → 执行(冒烟/功能/回归/兼容/性能) → 发布(灰度/线上应急)
```

1. **需求评审**：识别测试重点，评估工作量。
2. **测试设计**：用例 + 测试数据 + 环境准备。
3. **执行阶段**：
   - 冒烟：主流程可用
   - 功能：用例执行 + 缺陷记录
   - 回归：修复验证 + 无新引入
   - 兼容：主流机型 + 系统版本
   - 性能：关键指标监控
4. **发布**：灰度监控 + 线上应急。

### 核心业务路径

注册登录 → 商品浏览 → 加购 → 下单 → 支付 → 订单管理。每条路径都要在**正常网络、弱网、离线**三种条件下各跑一遍，因为移动端最真实的场景就是网络不稳。

### 安装与升级流程（易被忽视）

```
全新安装 → 启动引导 → 登录
旧版覆盖安装(全量/增量) → 数据迁移 → 启动校验
应用内强更/热修 → 重启生效
```

升级测试重点：旧版本用户数据能否平滑迁移、增量包是否完整、降级安装是否被拦。

## 测试策略

### 测试分层

| 类型     | 占比 | 目的           |
| -------- | ---- | -------------- |
| 单元测试 | 20%  | 核心业务逻辑   |
| 接口测试 | 30%  | 前后端数据交互 |
| UI 测试  | 35%  | 用户交互流程   |
| 专项测试 | 15%  | 性能/安全/兼容 |

### 测试重点

- **核心路径**：注册登录、浏览、下单支付、订单管理
- **边界场景**：网络中断、存储不足、权限拒绝
- **安全测试**：敏感数据加密、越权访问、注入

### 兼容性矩阵（优先级法）

不要"所有机型都测"，用**用户占比**切 Top 机型：

| 维度   | 取值                              |
| ------ | --------------------------------- |
| 品牌   | 华为/小米/Oppo/vivo/三星 + iPhone |
| 系统   | Android 10-14、iOS 14-17          |
| 分辨率 | 1080p / 2K / 折叠屏               |
| 网络   | WiFi / 4G / 弱网 / 离线           |

日常覆盖 Top 50，长尾交给云测平台批量跑。

### 状态流转测试

移动端状态比后台复杂，重点关注：

- **登录态**：token 过期、多端互踢、退出后本地数据清理
- **前后台切换**：切后台 30 分钟后回前台，页面/数据是否还原
- **网络切换**：下载中切 WiFi↔4G，任务是否续传
- **离线模式**：无网时操作，恢复网络后是否同步

### PO 模式封装

```python
# pages/goods_page.py  Page Object 封装页面元素与操作
from appium.webdriver.common.appiumby import AppiumBy

class GoodsPage:
    # 优先用 resource-id / accessibility-id，稳定且不易因布局变动失效
    ADD_CART = (AppiumBy.ID, "com.shop:id/btn_add_cart")

    def __init__(self, driver):
        self.driver = driver

    def add_to_cart(self):
        # 显式等待元素可点击，避免时序导致的 flaky
        el = WebDriverWait(self.driver, 10).until(
            EC.element_to_be_clickable(self.ADD_CART))
        el.click()
```

**关键实践**：统一元素定位策略（优先 ResourceID）；封装公共操作；定期维护脚本处理元素变更。

### 稳定性保障

```python
# 健壮等待 + 重试，降低 UI 自动化 flaky
def safe_click(driver, locator, retries=3):
    for i in range(retries):
        try:
            WebDriverWait(driver, 10).until(EC.element_to_be_clickable(locator)).click()
            return
        except Exception as e:
            if i == retries - 1:
                raise
            time.sleep(1)   # 指数退避更优，此处简写
```

## 故障和复盘

### 案例：弱网支付失败

**现象**：部分用户支付提示"网络异常"，实际扣款成功但订单未更新。
**根因**：回调超时过短 + 弱网回调丢失 + 缺主动查询补偿。
**修复**：优化回调超时、增加状态主动查询、建支付对账任务。
**测试改进**：增弱网支付专项、完善异常用例、加支付结果验证自动化。

```python
# 弱网支付专项：模拟回调丢失后应有主动查询补偿
def test_pay_callback_lost_then_query():
    pay_and_let_callback_lost()             # 构造回调丢失
    # 系统应在超时后主动查单，最终订单状态=已支付
    wait_until(lambda: order_status() == "PAID", timeout=30)
```

- **ANR**：主线程耗时操作，靠卡顿栈分析。

## 可能追问

**Q：如何处理机型碎片化？**
建机型优先级矩阵，按用户占比定 Top 50 重点机型；日常测高频机，兼容交给云测覆盖长尾；发现问题建机型特征库归纳共性。

**Q：自动化脚本如何保持稳定？**
三招：统一用稳定定位（ResourceID/AccessibilityID）；封装健壮等待与重试；建立维护机制定期清失效用例。

**Q：如何衡量覆盖率是否足够？**
多维度：需求覆盖（用例↔需求映射）、功能覆盖（场景↔模块）、代码覆盖（白盒）、风险覆盖（高风险深度）。

**Q：弱网测试怎么做？**
三类弱网（高延迟/高丢包/断网恢复）用 Charles/ATC 构造，重点测支付、下载、离线同步；验证失败可重试、数据不丢、恢复可续传。

**Q：安装升级测试有哪些坑？**
旧版数据迁移失败导致白屏/崩溃；增量包不完整致安装失败；降级安装未拦截。需覆盖全量/增量/强更/热修。

### 深挖式追问与参考回答

移动端项目的深挖追问通常围绕"数据和账号从哪来""你比纯后端测试多做了什么"，下面四组是高频问题。

**追问1：UI 自动化的账号和数据怎么准备？每次跑之前手工往手机里灌数据吗？**

参考回答：不用。账号用预置账号池，按测试套件分配独占账号，避免多任务登录互踢；业务数据全部走接口造——App 自动化开始前先调后端接口把商品、订单、优惠券造好，App 层只负责"消费"这些数据。这样 UI 用例和后端接口测试共享同一套造数服务，数据失效时两类用例一起报警，定位也快。唯一例外是本地缓存、离线数据这类端内状态，只能靠 App 操作和文件注入构造。

**追问2：移动端项目的接口测试，和纯后端项目的接口测试有什么区别？**

参考回答：接口本身一样，区别在三点。第一，请求上下文要模拟端上行为：设备号、版本号、渠道包标识这些 header 后端会拿来做事（灰度、风控、下发配置），漏了就测出假结果；第二，弱网和中断是常态：同一接口在超时重试、断线重连下的表现必须验证，纯后端项目没有这个维度；第三，版本兼容：后端一套代码，端上七八个历史版本同时在网，接口必须向后兼容，我们专门有「旧版本回归集」跑在主版本发版前。

**追问3：UI 自动化只覆盖冒烟和核心路径，为什么不是越多越好？**

参考回答：ROI 决定的。UI 自动化是所有分层里成本最高、稳定性最低的一层：脚本维护贵、执行慢、对环境抖动敏感。把业务校验尽量下沉到接口层（同样的登录、下单、支付，接口层几秒跑完），UI 层只留"用户真的要用这个按钮走完这条路"的验证。判断标准：用例验证的是界面交互本身（按钮、跳转、展示）就留 UI 层，验证的是业务规则就下沉。按这个标准裁剪后，UI 用例更精简，稳定性反而上来了。

**追问4：iOS 和 Android 双端，自动化是共用一套脚本还是各写各的？**

参考回答：框架层共用、定位层分开。Page Object 的业务方法（登录、加购、下单）抽象成统一接口，测试步骤和断言只写一份；元素定位和驱动按平台各配一份定位表（参考 [页面对象模式](/testdev-interview-site/glossary/page-object-pattern/)）。好处是新增业务场景用例写一遍、双端都能跑；代价是抽象设计要克制——页面差异大的场景不强求统一，否则 PO 里全是 if android else，可读性反而崩了。

## 项目难点与解决

### 难点一：UI 自动化 flaky 严重，CI 结果没人信

**问题**：Appium 用例本地能过、CI 上随机挂，同一批用例两次执行结果不同，团队默认"红了就重跑"，自动化形同虚设。

**分析**：拉一个月的失败记录归因：真正的产品缺陷不到两成，其余是定位失效、等待不足、设备状态残留三类工程问题，本质是脚本对"不确定时间"的处理太粗糙。

**方案**：三管齐下。定位统一收敛到 resource-id/accessibility-id，推动前端补齐测试属性；等待全部改为显式等待封装，禁止裸 sleep；每条用例执行前强制清理 App 数据，消除设备状态残留。再配一层失败自动重试加截图留痕（参考 [重试机制](/testdev-interview-site/coding/retry-mechanism/)），重试通过的单独标黄、每周复盘清理。

**结果**：UI 用例稳定性提升到 95% 以上，CI 结果重新成为发版依据（示例数字请替换成你的真实数据）。

### 难点二：机型碎片化，全量真机不可能，漏测又担责

**问题**：Android 300+ 机型不可能全测，但每次线上问题追责第一句就是"怎么没测这台机器"。

**分析**：碎片化的正确解法是分层覆盖而不是穷举：高频机型代表大多数用户，长尾机型的问题大多能归因到有限的几类——分辨率、系统版本、厂商 ROM 行为差异。

**方案**：按月更新机型 Top 榜，Top 50 真机日常覆盖，重点版本叠加人工探索；长尾机型走云测平台跑「安装、启动、核心路径」三件套；建立机型特征库，把"某厂商后台杀进程""某系统权限默认关闭"这类已知差异沉淀成检查项，新版本评审时按特征库圈定重点关注机型。

**结果**：兼容类线上问题环比下降，且每类问题都能回答"为什么没测到"——要么不在 Top 榜（用户占比极低），要么特征库已补上对应检查项（示例表述，请换成你的真实经历）。

### 难点三：双端发版节奏不一致，回归窗口对不齐

**问题**：iOS 审核时间不可控、Android 先发，「双端同步迭代」实际变成 Android 先上线、iOS 滞后一周，回归和线上监控窗口错开。

**分析**：与其追双端同日发版，不如把质量动作从"发版窗口"解耦出来，前置到合码阶段——质量保障不依赖发版日，发版日期就不敏感了。

**方案**：接口层回归整体前置，双端共用同一套接口回归集，任何一端合码都触发；UI 冒烟改成每日定时而非发版触发；发版检查清单按平台拆分——Android 侧重渠道包和升级链路，iOS 侧重审核合规与热更禁用场景，避免互相等待。

**结果**：双端发版日期仍不重合，但质量保障动作不再依赖发版日，灰度期问题拦截率明显提升（示例数字请替换）。

## 常见错误

### 错误1：用 XPath 绝对路径定位

```python
# 错误：布局一变就失效
driver.find_element(AppiumBy.XPATH, "/hierarchy/android.../btn[3]")
# 正确：用稳定的 resource-id
driver.find_element(AppiumBy.ID, "com.shop:id/btn_add_cart")
```

### 错误2：忽略前后台切换

```python
# 错误：只在首屏验证状态
# 正确：切后台 N 分钟再回前台，验证状态还原
driver.background_app(1800)   # 后台 30 分钟
assert page_restored()        # 回前台后数据/页面应还原
```

### 错误3：只在 WiFi 下测支付

```python
# 错误：默认网络下通过就认为 OK
# 正确：必须补弱网/离线场景，验证失败可重试、数据不丢
```
