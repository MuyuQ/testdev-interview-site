## 1. 场景题原问

> "我们下单链路拆成了订单服务、库存服务和支付服务,三个服务各自有数据库。用户下单时要同时扣库存、创建订单、发起支付。请设计测试方案,保证分布式事务的数据一致性。"

## 2. 先确认问题边界

分布式事务题最容易直接背 SAGA、TCC 名词就开写。先确认边界,回答质量立刻不同:

- **事务模式**:同步调用链(订单 → 库存 → 支付)、消息驱动(本地消息表 + MQ),还是 SAGA 编排/协同?
- **一致性要求**:是强一致(必须同时成功或同时失败),还是最终一致(允许秒级到分钟级中间状态)?
- **失败频率假设**:网络抖动、服务超时、支付成功但订单创建失败的组合,系统是否已有补偿机制?
- **隔离性要求**:中间状态是否对用户可见?例如"已扣库存但订单未创建"时,用户端显示什么?
- **对账体系**:是否已有定时对账、差异处理工单流程?测试要不要覆盖对账本身?
- **规模**:峰值下单 QPS 多少?决定了性能测试里并发冲突的强度。

一个高分的开场是:"我先确认一下系统当前的事务模式和一致性预期,因为同步链路和消息驱动的失败注入点完全不同。"

## 3. 风险分析

| 风险类型       | 具体表现                       | 用户感知             |
| -------------- | ------------------------------ | -------------------- |
| **部分成功**   | 库存扣了、订单没建             | 库存少了却查无此单   |
| **重复提交**   | 网络重试导致同一订单扣两次库存 | 超卖或多扣           |
| **悬挂操作**   | 补偿先到、原操作后到           | 已取消的单又扣了库存 |
| **状态不一致** | 支付成功但订单仍"待支付"       | 重复支付或退款纠纷   |
| **消息丢失**   | MQ 投递失败或消费异常          | 流程中断且无感知     |
| **对账缺口**   | 极端场景未覆盖对账规则         | 差异数据长期滞留     |

其中"悬挂操作"最容易被漏测:补偿请求先于原请求到达(Try 超时但实际成功,Cancel 先执行,之后 Try 才到达),需要空回滚与幂等设计兜底。

## 4. 测试维度

### 4.1 功能维度

- **正常链路**:三服务全部成功的端到端验证,各库数据一致
- **状态可见性**:每个中间状态下,订单详情页、库存中心、支付中心的展示正确

### 4.2 一致性维度(核心)

- **部分失败矩阵**:三个服务各作为"第一个失败点",验证补偿是否把已完成步骤全部回滚
- **最终一致时间窗**:注入失败后,多长时间内数据恢复一致,是否符合 SLA
- **幂等性**:同一笔事务消息重复投递,只应生效一次
- **空回滚与悬挂**:Cancel 先于 Try 到达,后续 Try 应被拒绝

### 4.3 异常维度

- **网络分区**:库存服务超时但实际成功(Try 超时假死)
- **消息可靠性**:MQ 不可用、消息重复、消息乱序
- **补偿失败**:补偿本身失败,是否进入重试队列与人工工单

### 4.4 性能与稳定性维度

- **并发冲突**:同一 SKU 高并发扣减,验证不超卖
- **补偿风暴**:批量失败触发大量补偿,验证系统不被打垮
- **对账时效**:百万级数据量下对账任务的执行时长与差异检出率

## 5. 核心用例设计

### 5.1 部分失败补偿矩阵(示例节选)

| 用例编号 | 注入点                | 预期结果                          |
| -------- | --------------------- | --------------------------------- |
| TC-DT-01 | 库存扣减失败          | 订单不创建,支付不发起,无脏数据    |
| TC-DT-02 | 订单创建失败          | 库存回滚到原值,支付不发起         |
| TC-DT-03 | 支付超时(实际未扣款)  | 订单取消,库存回滚                 |
| TC-DT-04 | 支付超时(实际已扣款)  | 订单补建或退款,库存按业务规则处理 |
| TC-DT-05 | 补偿请求重复投递      | 只回滚一次,幂等生效               |
| TC-DT-06 | Cancel 先于 Try(悬挂) | 空回滚记录,Try 到达后被拒绝       |

### 5.2 失败注入示例(Python + pytest)

```python
import pytest
from chaos import fault_injector  # 团队内的故障注入封装

@pytest.mark.distributed_transaction
class TestPartialFailureCompensation:
    """部分失败补偿矩阵:每个服务轮流做失败点"""

    @fault_injector(target="inventory-service", action="timeout", duration_ms=3000)
    def test_inventory_timeout_triggers_compensation(self, order_api, db_checker):
        """库存超时:订单应取消,库存最终回滚"""
        resp = order_api.create_order(sku="SKU-001", count=1)

        assert resp.status in ("CANCELLED", "CREATING")
        # 等待补偿完成,验证最终一致性
        db_checker.wait_until(
            lambda: db_checker.inventory("SKU-001") == db_checker.INITIAL_STOCK,
            timeout=10,
        )
        db_checker.assert_order_status(resp.order_id, "CANCELLED")

    def test_duplicate_compensation_is_idempotent(self, order_api, db_checker):
        """补偿消息重复投递:库存只回滚一次"""
        resp = order_api.create_order(sku="SKU-002", count=2)
        order_api.force_fail_and_compensate(resp.order_id)
        # 人为重放同一条补偿消息
        order_api.replay_compensation_message(resp.order_id)

        db_checker.wait_until(
            lambda: db_checker.inventory("SKU-002") == db_checker.INITIAL_STOCK,
            timeout=10,
        )
        # 重放后库存不应多回滚
        assert db_checker.inventory("SKU-002") == db_checker.INITIAL_STOCK
```

### 5.3 对账验证

对账测试的思路不是"跑一遍对账任务",而是**故意注入差异,验证对账能发现并驱动处理**:

```text
用例 TC-DT-09:
  前置:直接改库,让订单库存在一笔"已支付"但支付库无对应记录的订单
  执行:触发对账任务
  预期:
    1. 对账报告出现该差异,差异类型为"支付缺失"
    2. 生成差异工单,状态为待处理
    3. 按工单执行差异处理接口后,数据恢复一致
```

## 6. 异常、边界和兼容情况

- **金额边界**:0 元订单、优惠后 0.01 元订单走分布式事务,部分平台会走不同链路
- **跨币种/跨境**:涉及汇率转换的事务,补偿时汇率快照是否被保留
- **大事务拆分**:一个订单包含多商家商品时,拆单后每个子单独立事务,部分拆单失败的处理
- **灰度兼容**:新旧链路共存期间,同一订单可能一半走旧逻辑一半走新逻辑
- **时钟偏差**:各服务时钟不同步时,基于时间戳的对账可能产生误报

## 7. 自动化策略

```text
层级一(每次提交):单服务事务逻辑的单测,Mock 下游,验证 Try/Confirm/Cancel 逻辑完整
层级二(每日):跨服务补偿链路自动化,固定失败注入矩阵在测试环境全量执行
层级三(每周):全链路混沌演练,随机注入超时、宕机、消息丢失,输出一致性恢复报告
层级四(每日):生产对账任务,差异工单闭环,把线上数据差异率作为质量指标
```

失败注入要做成**基础设施能力**而不是手工操作:测试平台提供"指定订单号 + 指定服务 + 指定动作"的注入 API,用例里一行装饰器即可启用,并且只在测试环境生效。

## 8. 数据准备和环境依赖

- **三库环境**:订单、库存、支付各独立数据库,禁止测试环境共用库偷懒,否则验证不了真实的一致性
- **基础数据**:每个 SKU 记录初始库存快照,用例前后可校验"库存守恒"
- **消息巡检工具**:能查询 MQ 中某业务键的消息条数与状态,验证消息投递与重放
- **时间控制**:可注入时钟偏移的测试环境,用于对账窗口边界验证
- **对账沙箱**:对账任务支持指定时间窗重跑,便于用例反复验证

## 9. 监控、告警和回滚

- **一致性指标**:中间状态滞留数(超过 X 分钟仍"处理中"的订单数)必须有监控与告警
- **补偿成功率**:补偿失败率上升说明依赖服务异常,应触发告警
- **对账差异率**:差异率超过阈值(如 0.01%)P0 告警,冻结相关发布
- **人工介入通道**:补偿和对账都失败时,必须有运营工单兜底流程,测试要验证这条人工链路真的可用

## 10. 面试回答骨架

> "我会先确认事务模式和一致性预期——同步链路用 TCC 类补偿,消息驱动用本地消息表加最终一致。测试设计分四层:第一层是失败注入矩阵,让每个服务轮流当失败点,验证补偿回滚完整;第二层是幂等与悬挂,验证重复消息和 Cancel 先到这类极端时序;第三层是对账,我会故意在库里注入差异,验证对账任务能发现并生成工单;第四层是监控,把中间状态滞留数和补偿成功率做成指标。在我上一个项目里,我们用这套方法把线上数据差异从每周十几笔降到月均一两笔,且都有工单闭环。"

要点:先澄清边界 → 分层展开 → 有失败注入的具体手段 → 有量化结果收尾。

## 11. 面试官可能追问

**追问 1:TCC 和 SAGA 怎么选?测试关注点有什么区别?**

参考回答:TCC 适合短事务、强一致性要求高的资金类操作,测试重点在 Try/Confirm/Cancel 三段逻辑、空回滚和悬挂;SAGA 适合长流程,每一步都有显式补偿,测试重点在补偿链完整性和中间状态的业务可见性。SAGA 没有 Try 阶段隔离资源,所以要额外验证中间状态期间的业务规则(比如"处理中"的库存是否还可被其他订单占用)。

**追问 2:怎么测"最终一致"的最终?时间窗怎么定?**

参考回答:时间窗来自业务 SLA,比如"支付成功后 30 秒内订单状态必须同步"。测试上用 `wait_until` 轮询断言,超时时间设为 SLA 的 1.5 倍;同时在监控层把"滞留超过 SLA 的事务数"做成告警指标。验证手段是注入失败后计时,统计数据恢复一致的分布,而不仅仅是单次通过。

**追问 3:如果补偿逻辑本身有 Bug,测试怎么发现?**

参考回答:三层防线。第一,补偿逻辑的单测与普通代码同等覆盖,尤其是边界(补偿时下游状态已变);第二,混沌演练随机注入,不预告注入点,让补偿路径在"非设计路径"上被触发;第三,对账兜底,对账规则独立于补偿逻辑实现,避免两套代码共享同一个错误假设。

**追问 4:并发下的超卖怎么测?**

参考回答:用多线程/协程并发脚本对同一 SKU 发起扣减,断言"成功扣减总数 ≤ 初始库存",同时校验每笔成功订单都有对应库存流水;再叠加数据库层唯一约束验证,防止应用层锁失效。相关方法在[库存扣减场景](/testdev-interview-site/scenario/inventory-deduction/)里有完整展开。
