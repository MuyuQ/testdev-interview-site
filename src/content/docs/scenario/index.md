## 模块定位

场景题模块解决的核心问题是：**面试时被问到"这个业务场景你会怎么测"，如何从风险分析到测试策略给出完整答案**。

传统的测试学习往往停留在"会写测试用例"，但面试考察的是"能否从业务场景出发，识别风险、拆解维度、设计策略"。这个模块通过真实业务场景（支付回调、登录鉴权、异步任务、数据迁移等），训练你形成一套可复用的场景分析方法论。

每个场景题页面都包含：面试原问、问题边界确认、风险分析、测试维度拆解、核心用例设计、自动化策略、异常边界处理、面试回答骨架。这不是让你背诵答案，而是掌握"问什么场景都能答"的分析框架。

## 内容分组

### 基础组：理解场景题答题框架

- 学习"先确认问题边界"的答题习惯
- 掌握"风险分析 → 测试维度 → 核心用例"的分析路径
- 理解功能、性能、安全、兼容四维测试模型

**入口**：[登录鉴权](/testdev-interview-site/scenario/login-auth/) 是最适合入门的场景，业务直观、风险点清晰。

### 实践组：动手设计测试用例

- 每个场景题都提供核心用例代码示例
- 建议在自己项目中复现至少一个场景的测试用例
- 练习将"面试回答骨架"转化成实际项目描述

**入口**：[支付回调](/testdev-interview-site/scenario/payment-callback/) 的幂等性测试用例最适合动手实践。

### 面试组：背诵标准表达模板

- 每个场景题末尾都有"面试回答骨架"
- 重点掌握开场白、核心展开、项目成果的三段式结构
- 准备应对"追问"的标准应答要点

**入口**：所有场景题的面试回答骨架都需要背诵，优先 [登录鉴权](/testdev-interview-site/scenario/login-auth/) 和 [支付回调](/testdev-interview-site/scenario/payment-callback/)。

### 进阶组：分布式系统测试思维

- 研究 [异步任务](/testdev-interview-site/scenario/async-task/) 的消息队列可靠性测试
- 理解幂等性、最终一致性、分布式事务等概念
- 掌握混沌测试、契约测试等进阶方法

**入口**：[分布式事务](/testdev-interview-site/scenario/distributed-transaction/) 是分布式思维的集中演练，[库存扣减](/testdev-interview-site/scenario/inventory-deduction/) 和 [订单取消](/testdev-interview-site/scenario/order-cancel/) 分别覆盖并发守恒与竞态仲裁两个高频追问方向。

## 最小完成标准

完成以下内容，才算基本掌握场景题模块：

1. **至少完成 3 个场景题的学习**（登录鉴权、支付回调、异步任务为必学）
2. **能独立回答"你会怎么测这个场景"的框架性问题**，包含：风险分析、测试维度、核心用例、自动化策略
3. **背诵至少 2 个场景题的面试回答骨架**，能流畅输出 2-3 分钟的回答
4. **能将场景题中的测试用例设计方法迁移到自己项目**，在简历或面试中讲述自己项目的测试方案

## 常见误区

| 误区                                  | 正确理解                                                                             |
| ------------------------------------- | ------------------------------------------------------------------------------------ |
| **误区1：背诵用例列表就够了**         | 场景题考察的是分析框架，不是用例数量。面试官换个场景，你还能用同样的方法分析才是关键 |
| **误区2：场景题只适合面试，不做项目** | 场景题的测试策略可以直接指导实际项目测试设计，支付回调的幂等性测试就是实战必备       |
| **误区3：先学完所有场景再面试**       | 掌握 3-4 个高频场景（登录、支付、异步任务）就够应对大多数场景题追问                  |
| **误区4：只看不动手**                 | 不动手写测试用例，面试时讲不出代码细节，容易被追问卡住                               |
| **误区5：忽视追问准备**               | 每个场景题的"面试官可能追问"是高频考点，必须准备应答要点                             |

## 场景题答题方法论：三步组织任何场景题

本模块 7 个场景各不相同，但答题的组织方式是同一个：**30 秒澄清收敛边界 → 风险矩阵决定优先级 → 分层作答展开细节**。学会这套方法，面对没准备过的场景题（优惠券、红包、评价系统）也不会无话可说。

### 第一步：30 秒澄清，消灭答题方向错误

场景题最大的失分不是"用例想少了"，而是"方向错了"——面试官心里想的是秒杀库存，你按普通下单去答，后面全部白费。开场 30 秒的澄清，作用是把开放题收敛成有边界的具体题。

澄清问题分三类，每类准备 1-2 个：

| 问题类型   | 目的           | 示例问法                                               |
| ---------- | -------------- | ------------------------------------------------------ |
| 业务规则类 | 确认流程和约束 | "下单后 15 分钟未支付会自动取消吗？取消后库存回补吗？" |
| 技术架构类 | 确认方案选型   | "库存是数据库直接扣减，还是 Redis 预扣再异步落库？"    |
| 质量属性类 | 确认测试侧重   | "这个系统最怕资损，还是最怕卡顿？允许的误差是多少？"   |

两个使用要点：

- **澄清不追求问全，追求问对**。30 秒内挑 2-3 个最能改变答案的问题，然后明确说："我先基于这几个假设作答，如果和实际不符请纠正我。"这样即使没问全，假设也摆在明面上，面试官会主动补齐。
- **每个澄清都要能影响后续回答**。问"日均订单量多少"是为了决定压测强度和自动化比例，不是为了问而问。澄清完能顺带点出影响："那并发量级大概到万级 QPS？我后面会重点讲削峰方案的验证。"

### 第二步：风险矩阵，决定"先讲什么"

边界确认后，把风险列出来但不要平均用力。用"发生概率 × 影响程度"两轴排序：

|            | 影响小       | 影响大                       |
| ---------- | ------------ | ---------------------------- |
| **概率高** | 讲一句带过   | 重点展开（核心用例从这里挑） |
| **概率低** | 可以不主动讲 | 讲到但压缩为"我会专项覆盖"   |

以登录鉴权为例：Token 过期处理不当是"高概率 × 高影响"（几乎必然发生，直接伤害用户），放重点；Token 被盗用是"低概率 × 高影响"（资损严重但罕见），压缩成"安全专项覆盖越权、重放、篡改"；验证码偶发延迟是"高概率 × 低影响"，一句带过。

面试时把这层排序说出来："这些风险我按发生概率和影响程度排了序，先讲高优的"——这句话本身就是加分项，它展示的是测试工程师的核心能力：**在有限时间里把资源投给风险最大的地方**。

### 第三步：分层作答，2 分钟讲出层次

标准时间分配（以 2 分钟回答为例）：

| 时间       | 内容       | 要点                                           |
| ---------- | ---------- | ---------------------------------------------- |
| 0-15 秒    | 澄清与假设 | 复述边界："我假设是 JWT 鉴权、允许双端登录"    |
| 15-45 秒   | 风险与维度 | 3-4 个风险点，归入功能/安全/一致性/性能        |
| 45-90 秒   | 核心用例   | 挑 2 个最高优风险讲细节：前置、步骤、断言      |
| 90-110 秒  | 保障策略   | 哪些自动化、哪些手工、监控什么指标             |
| 110-120 秒 | 量化收尾   | 项目中的结果数字，或"这套方法在 XX 项目验证过" |

最容易被忽视的是"核心用例讲细节"这一步。很多候选人风险讲得很全，但每条都停留在"我会测 Token 过期"一句话，面试官追问"具体怎么测"就卡住。正确做法是主动展开一个："比如 Token 过期，我会把 exp 设成过去时间签一个 JWT 直接请求受保护接口，断言返回 401 和明确的错误码，而不是静默放行。"有前置、有步骤、有断言，可信度立刻不同。

### 应对答不上来的追问

被问到没准备过的问题时，三条退路都比沉默强：

1. **承认边界 + 给分析路径**："这个我没实际测过，但按同样的方法我会先确认 XX，再从 XX 和 XX 两个方向设计用例。"面试官考察的是方法，不是记忆。
2. **关联已学场景**："这和支付回调的幂等验证思路接近，区别在于 XX。"把新问题挂到熟悉的知识树上。
3. **反问澄清再作答**：刁钻的追问往往缺条件，先问一句"您指的是并发场景还是单笔场景？"把开放题变具体题，这本身就是场景题训练的能力。

### 用一道没学过的题检验框架

以"优惠券系统怎么测"为例走一遍：

1. **澄清**：券的类型（满减/折扣/兑换码）？能否叠加？过期和退回规则是什么？
2. **风险矩阵**：高概率高影响——叠加使用时价格计算错误；低概率高影响——并发领券超发；高概率低影响——到期提醒文案错误。
3. **分层作答**：先答面额计算与叠加规则的功能用例，再答并发领取的守恒验证（参考[库存扣减](/testdev-interview-site/scenario/inventory-deduction/)的思路），最后补自动化——价格计算天然适合参数化断言。

能把这个框架套到陌生场景上，就达到了本模块的目标："一题通百题"。要训练连续追问下的应对，进入[面试追问链](/testdev-interview-site/interview-chains/)；测试设计的底层方法见[测试设计](/testdev-interview-site/glossary/test-design/)。
