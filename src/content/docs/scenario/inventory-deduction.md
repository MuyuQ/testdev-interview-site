## 1. 场景题原问

> "我们有一个秒杀活动,热门商品库存 1000 件,预计瞬时 5 万人抢购。请设计测试方案,保证库存扣减不超卖、不少卖,并评估系统在高并发下的表现。"

## 2. 先确认问题边界

库存题的答案完全取决于方案选型,先问清楚:

- **扣减方式**:数据库行锁(`UPDATE stock SET count = count - 1 WHERE count > 0`)、Redis 预扣 + 异步落库、还是库存分桶?
- **下单与扣减的时序**:先扣库存再创建订单(预占模式),还是先创建订单再扣减?
- **预占释放规则**:预占后多久未支付释放?支付失败回补吗?取消订单回补吗?
- **幂等键**:同一用户重复点击、网络重试,用什么保证只扣一次(订单号幂等?令牌?)
- **可接受超卖率**:业务上是否绝对不允许超卖,还是允许极小概率事后补偿?
- **活动特征**:持续性抢购还是瞬时秒杀?有没有预约、分层放量的运营规则?

## 3. 风险分析

| 风险类型       | 具体表现                      | 后果                           |
| -------------- | ----------------------------- | ------------------------------ |
| **超卖**       | 并发读旧库存,双双扣减成功     | 发不出货,赔付与舆情            |
| **少卖**       | 回补丢失、预占未释放          | 库存虚低,卖不出去              |
| **重复扣减**   | 网络重试、用户狂点            | 一单扣多次,用户损失            |
| **热点行锁**   | 单行更新串行化                | 吞吐骤降、请求超时、连接池打满 |
| **缓存不一致** | Redis 与 DB 扣减数对不上      | 展示库存与真实库存偏离         |
| **回补风暴**   | 大量订单超时释放,回补消息堆积 | 二次超卖或延迟可见             |

"少卖"和超卖一样致命但常被漏测:预占释放、支付失败回补、取消回补三条路径任何一条丢消息,库存就永久少一件。

## 4. 测试维度

### 4.1 正确性维度(核心)

- **守恒验证**:初始库存 = 成功扣减 + 剩余库存,活动结束后逐 SKU 核对
- **流水核对**:每笔成功订单都有且只有一条扣减流水,流水总额与库存差值一致
- **回补完整性**:每笔取消/超时/支付失败的订单都有对应回补流水

### 4.2 并发维度

- **同 SKU 并发扣减**:N 并发抢 M 件,断言成功数恰为 M
- **多 SKU 混合并发**:验证不同 SKU 之间互不干扰
- **同一用户并发**:同一用户同时发两次请求,只成功一次(幂等)
- **扣减与回补并发**:扣减进行中同时触发超时释放,验证总量守恒

### 4.3 性能维度

- **吞吐与延迟**:扣减接口在目标 QPS 下的 P95/P99 延迟
- **热点行表现**:行锁方案下单行 TPS 上限,超时率随并发的变化曲线
- **削峰验证**:MQ 异步落库时,峰值积压量与消费追平时间

### 4.4 异常维度

- **Redis 宕机**:预扣缓存在位时的降级策略是否按预期(拒绝写入还是落 DB)
- **回补消息丢失**:验证有定时对账任务发现"已取消未回补"的差异
- **库存为 0 后的流量**:售罄后的请求被快速拒绝且不影响其他 SKU

## 5. 核心用例设计

### 5.1 并发扣减守恒用例(Python)

```python
import threading
import httpx

def test_no_oversell_under_concurrency(stock_api, db_checker):
    """100 件库存,200 并发请求:成功数恰好 100,守恒成立"""
    sku = "SECKILL-001"
    initial = db_checker.stock(sku)  # 前置:确认为 100

    success, fail = [], []
    barrier = threading.Barrier(200)  # 同时起跑,放大竞争

    def grab():
        with httpx.Client(base_url=stock_api.BASE) as client:
            barrier.wait()
            user_id = f"user-{threading.get_ident()}"
            resp = client.post("/seckill", json={"sku": sku, "userId": user_id})
            (success if resp.status_code == 200 else fail).append(resp)

    threads = [threading.Thread(target=grab) for _ in range(200)]
    for t in threads: t.start()
    for t in threads: t.join()

    final = db_checker.stock(sku)

    # 断言 1:成功订单数不超过库存
    assert len(success) == 100, f"成功 {len(success)} 笔,应恰好 100"
    # 断言 2:守恒
    assert initial == len(success) + final, "库存守恒被破坏"
    # 断言 3:流水与订单一一对应,无重复扣减
    flows = db_checker.stock_flows(sku)
    assert len(flows) == 100
    assert len({f["order_id"] for f in flows}) == 100
```

## 6. 异常、边界和兼容情况

- **库存为 0**:继续请求应快速失败,响应里不应泄露负数库存
- **边界值**:库存恰好剩 1 件时 2 个并发,恰 1 成功;库存为 1 时取消回补后再抢,可再成功 1 次
- **重复点击**:前端按钮置灰失效时,直接调接口仍被幂等挡住
- **活动叠加**:同一 SKU 同时参与满减与秒杀,两套扣减逻辑的先后与一致性
- **分桶库存**:桶间不均导致部分桶提前售罄(伪少卖),需要验证再平衡逻辑

## 7. 自动化策略

```text
单测层:扣减服务单测,Mock 仓储层,覆盖"够扣/不够扣/并发注入口"的分支
接口层(每日):守恒断言 + 幂等断言脚本,小规模(50 并发)稳定跑
专项层(大促前):真实压测平台执行三套性能场景,输出守恒核对报告
线上层(大促中):实时守恒监控——每分钟对账"成功订单数 vs 扣减流水数",偏差即告警
```

并发用例要可重复:每次跑之前重置 SKU 库存与流水表,断言里不允许出现"大概、差不多"——库存是少数可以做到绝对守恒断言的领域。

## 8. 数据准备和环境依赖

- **独立压测环境**:压测流量不能进生产,SKU 数据与生产隔离
- **库存快照工具**:跑用例前记录初始值,跑完后一键核对守恒
- **流水表可查**:扣减、回补流水带业务键(order_id、user_id),支持按 SKU 汇总
- **时间可控**:能模拟"预占超时"而不用真等 15 分钟(时间服务可注入偏移)
- **影子库存**:压测用影子 SKU,避免污染展示数据

## 9. 监控、告警和回滚

- **核心指标**:剩余库存、扣减 TPS、超时率、MQ 积压深度、回补成功率
- **守恒巡检**:定时任务比对"成功订单总数 + 剩余库存 = 初始库存",破坏守恒立即 P0
- **热点发现**:单 SKU 扣减 TPS 突增时自动扩容连接池或触发限流
- **回滚预案**:预扣方案异常时切回 DB 扣减的开关,测试需验证开关切换后数据一致

## 10. 面试回答骨架

> "库存题我会围绕三个词回答:守恒、幂等、削峰。守恒是断言基准——初始库存等于成功扣减加剩余,每笔订单对应唯一流水,我用 200 并发抢 100 件的脚本验证过;幂等靠订单号幂等键,覆盖重复点击和网络重试;削峰看方案——行锁方案我会压出热点行 TPS 上限,预扣方案我会验证 Redis 宕机降级和回补完整性。最后加一层线上守恒巡检,任何偏差立即告警。在我做的秒杀项目里,这套方案上线后大促零超卖,回补差异都能在对账里闭环。"

要点:三个关键词组织回答 → 每个词都有具体验证手段 → 有结果数字。

## 11. 面试官可能追问

**追问 1:Redis 预扣和数据库行锁,测试关注点有什么不同?**

参考回答:行锁的正确性由数据库保证,测试重点在性能(热点行 TPS、锁等待)和超时后的用户体验;Redis 预扣把正确性责任转移到了应用层,测试重点变成 Redis 与 DB 的最终一致、宕机降级、回补完整性,以及 Lua 脚本原子性的边界验证。方案越分布,守恒断言和对账越重要。

**追问 2:怎么测"少卖"?**

参考回答:少卖来自回补丢失。我会列出所有回补触发点(超时释放、支付失败、取消、风控拦截),逐个注入"回补消息丢失",验证对账任务能在下个周期发现差异并自动或人工回补。同时做长时间稳定性:连续 24 小时循环下单-取消,守恒断言不允许出现累积偏差。

**追问 3:压测时怎么区分是库存服务的问题还是下游的问题?**

参考回答:全链路标记压测流量(影子订单号),各服务的 APM 都能按标记过滤;同时用阶梯加压找到拐点——如果 TPS 在库存服务更新 QPS 先到瓶颈,是库存问题;如果是下游创建订单先报错,再看具体错误分布。压测报告要给出每个环节的容量水位,而不是只有一个总 TPS。

**追问 4:如果要你设计库存分桶,怎么验证分桶正确性?**

参考回答:功能上验证路由一致性(同一请求两次路由到同桶)、再平衡触发条件(某桶售罄后从其他桶调拨);并发上验证跨桶调拨期间的守恒,调拨也必须有流水;异常上验证桶数据损坏时的兜底(对账重算)。分桶把单行热点拆成多行,但也把"一个总数"变成"多个局部和",守恒断言要升级为对桶内与桶间分别核对。
