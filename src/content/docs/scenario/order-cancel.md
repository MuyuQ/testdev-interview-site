## 1. 场景题原问

> "我们的订单模块支持用户主动取消、超时自动取消、客服代客取消三种方式。请设计测试方案,覆盖取消的状态流转、库存回补和已支付订单的退款联动。"

## 2. 先确认问题边界

- **取消时机窗口**:哪些订单状态允许取消?待支付可以,已支付是否可以,已发货呢?
- **取消方式**:用户端自助取消、超时系统取消、客服后台取消,三者权限和触发链路不同
- **资源占用清单**:订单占用了哪些需要回补的资源——库存、优惠券、积分抵扣、限购资格、赠品
- **退款规则**:已支付订单取消是原路退款还是退余额?退款时效承诺多久?
- **并发场景**:取消的同时可能发生支付回调、发货确认、申请开票,系统如何裁决
- **审计要求**:取消原因是否必填,风控是否需要拦截高频取消用户

## 3. 风险分析

| 风险类型         | 具体表现                           | 后果                  |
| ---------------- | ---------------------------------- | --------------------- |
| **状态机漏洞**   | 非法状态也能取消(已发货被取消成功) | 货已发出但订单关闭    |
| **回补遗漏**     | 取消成功但库存没回来               | 少卖                  |
| **回补重复**     | 重复取消触发多次回补               | 虚高库存,可能超卖     |
| **取消支付竞态** | 取消与支付回调并发                 | 状态与资金流不一致    |
| **退款失败静默** | 退款单创建失败无人感知             | 用户钱货两空,投诉升级 |
| **超时取消风暴** | 大量待支付单同一时刻过期           | 取消任务积压,回补延迟 |

竞态是本题的灵魂:取消和支付回调由不同外部方触发,到达顺序无法控制,测试必须显式覆盖"同时到达"。

## 4. 测试维度

### 4.1 状态机维度

- **合法迁移矩阵**:每个状态 × 取消动作,合法的应成功,非法的应拒绝并给出明确错误码
- **取消后终态**:取消是终态,验证取消后任何后续操作(支付、发货、确认收货)都被拒绝
- **状态展示**:用户端、商家端、客服端看到的取消状态与原因一致

### 4.2 回补维度

- **库存回补**:取消后可售库存 +1,回补流水关联订单号;重复取消只回补一次
- **优惠券恢复**:已使用的优惠券回到"未使用";已过期的优惠券不恢复但要有说明
- **积分与权益**:抵扣积分全额返还,赠送积分是否扣回按规则验证
- **限购资格**:限购商品取消后,用户购买资格恢复

### 4.3 退款联动维度

- **待支付取消**:不产生退款单,支付单关闭
- **已支付取消**:产生退款单,金额 = 实付金额(含积分抵扣的拆分展示),走原路
- **部分退款后取消**:先退了一部分再取消,剩余金额计算正确
- **退款失败**:支付渠道失败时重试与人工工单链路

### 4.4 并发与异常维度

- **取消 vs 支付回调**:两个请求并发,最终状态与资金一致(见 5.2)
- **取消 vs 发货**:已进入发货流程的订单取消被拦截,或走拦截成功/失败两个分支
- **重复取消**:幂等,第二次返回相同结果
- **超时任务堆积**:10 万订单同时到期,取消任务分批执行,回补无遗漏

## 5. 核心用例设计

### 5.1 状态迁移矩阵(节选)

| 当前状态 | 用户取消 | 超时取消 | 客服取消  | 预期                      |
| -------- | -------- | -------- | --------- | ------------------------- |
| 待支付   | ✅ 成功  | ✅ 成功  | ✅ 成功   | 回补库存与优惠券          |
| 已支付   | 按配置   | ❌ 拒绝  | ✅ 走退款 | 退款单创建                |
| 发货中   | ❌ 拒绝  | ❌ 拒绝  | 走拦截    | 拦截成功则退款,失败转拒收 |
| 已签收   | ❌ 拒绝  | ❌ 拒绝  | ❌ 拒绝   | 提示走售后退货            |
| 已取消   | 幂等返回 | 幂等返回 | 幂等返回  | 不重复回补                |

### 5.2 取消与支付回调竞态用例

```python
import threading
from concurrent.futures import ThreadPoolExecutor

def test_cancel_and_payment_callback_race(order_api, pay_mock, db_checker):
    """取消请求与支付成功回调同时到达:订单终态必须与资金一致"""
    order = order_api.create_unpaid_order(sku="SKU-100", count=1)

    barrier = threading.Barrier(2)

    def do_cancel():
        barrier.wait()
        return order_api.cancel(order.order_id, reason="test")

    def do_pay_callback():
        barrier.wait()
        return pay_mock.success_callback(order.order_id)

    with ThreadPoolExecutor() as pool:
        cancel_f = pool.submit(do_cancel)
        pay_f = pool.submit(do_pay_callback)
        cancel_resp = cancel_f.result()
        pay_resp = pay_f.result()

    final_status = db_checker.order_status(order.order_id)
    paid = db_checker.is_paid(order.order_id)

    # 一致性断言:状态与资金流必须匹配,不允许"已取消但已扣款"
    if paid:
        assert final_status in ("PAID_REFUNDING", "PAID"),
            "已扣款订单不能停在已取消状态"
        assert db_checker.refund_exists(order.order_id), "已扣款必须自动发起退款"
    else:
        assert final_status == "CANCELLED"

    # 无论哪个竞态胜出,库存最终只回补一次且守恒
    assert db_checker.stock_flows_count("SKU-100", order.order_id) == 1
```

## 6. 异常、边界和兼容情况

- **支付渠道延迟退款**:退款单创建成功但渠道处理慢,订单状态应为"退款中"而非"已取消"
- **取消原因枚举**:前端传入枚举外的值应被校验拦截
- **客服取消已发货订单**:走拦截流程,拦截失败自动转"拒收退款"分支
- **跨年/跨时区**:超时取消的任务时间戳处理,避免时区导致的提前或延迟取消
- **老订单兼容**:历史订单缺少取消原因字段的,取消流程不应报错

## 7. 自动化策略

```text
单测层:状态机单测——把迁移矩阵做成参数化用例,非法迁移断言错误码
接口层(每日):取消主链路 + 回补守恒 + 幂等,三段断言一个脚本
竞态层(每日):取消与支付回调并发脚本,固定跑 200 次竞态组合
任务层(每周):超时批量取消压测,验证任务分片与失败重试
线上层(持续):取消后 N 分钟回补核对告警——"已取消但库存未回补"的订单数
```

状态机矩阵参数化是性价比最高的做法:矩阵里每个格子都是一条用例,新增状态时补格子即可,不需要重写脚本。

## 8. 数据准备和环境依赖

- **多状态订单工厂**:一键构造任意状态的订单(待支付、已支付、发货中),支持指定优惠券、积分占用
- **支付 Mock**:可控的支付回调(成功/失败/延迟/重复),支撑竞态测试
- **库存流水可查**:按订单号查全部库存变动,守恒断言的基础
- **时间服务可注入**:超时取消场景不真等 15 分钟
- **退款通道沙箱**:模拟渠道退款成功、失败、延迟到账

## 9. 监控、告警和回滚

- **取消转化指标**:取消成功率、各状态拒绝分布(拒绝突增说明状态机或前端有 Bug)
- **回补时效**:取消完成后 X 分钟内库存未回补的订单数告警
- **退款时效**:退款单创建后超过 SLA 未到账的告警,联系渠道
- **竞态仲裁日志**:取消与支付回调冲突的裁决记录必须落日志,便于复盘争议订单
- **批量任务监控**:超时取消任务的分片进度、失败重试次数

## 10. 面试回答骨架

> "订单取消我会先画状态机:哪些状态允许取消、由谁触发,把迁移矩阵变成参数化用例。然后验证三类回补——库存、优惠券、积分,断言取消后守恒且重复取消不重复回补。最关键的是竞态:取消和支付回调同时到达,我会用双线程屏障构造并发,断言订单终态必须和资金流一致——已扣款就自动转退款,未扣款才允许停在已取消。最后补上超时批量取消的任务测试和线上回补时效监控。我曾在这个场景里抓到一个真实缺陷:客服取消已发货订单时拦截失败但订单被置为已取消,最后靠状态机矩阵用例修复后全绿。"

要点:状态机先行 → 回补守恒 → 竞态是重点 → 有真实缺陷故事收尾。

## 11. 面试官可能追问

**追问 1:取消和支付回调并发,系统层面应该怎么设计才可测?**

参考回答:核心是订单状态更新必须串行化(数据库乐观锁或分布式锁按订单号),每个请求带着前置状态检查做 CAS 更新,失败方读取最新状态重新路由——取消失败就转退款流程,支付回调发现已取消就走退款。可测性上,这种设计让并发结果收敛为两种合法终态,测试只需断言"状态与资金一致"这个不变量,而不需要猜时序。

**追问 2:怎么验证退款金额正确?**

参考回答:金额拆分对账——实付金额 = 现金 + 优惠券抵扣 + 积分抵扣,退款单必须按同一拆分回退,且各部分之和等于实付。用例要覆盖"部分使用优惠后再取消"和"渠道优惠与商家优惠叠加"的组合,断言写到每一类资金账户的变动流水,而不是只看一个总数。

**追问 3:超时取消任务挂了怎么办?**

参考回答:三重保障——任务失败重试与告警;巡检兜底定时扫描"超期未取消"订单补偿执行;监控指标暴露待支付订单的平均超龄时长。测试要验证:任务中途宕机重启后不重复取消(幂等),也不漏单(游标持久化)。

**追问 4:为什么说"取消是终态"?如果业务要支持取消后恢复呢?**

参考回答:取消作为终态能让下游所有系统(库存、优惠、物流)以单一事件收敛资源,回补逻辑只执行一次。如果业务要"取消恢复",更稳妥的建模是把"恢复"定义成一个新订单或反向流程(重新占用资源),而不是把已取消订单拉回旧状态——否则所有回补都要设计成可逆,复杂度指数级上升。测试上我会要求:恢复流程必须生成新的资源占用流水,并且新旧流水可追溯。
